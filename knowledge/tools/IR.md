# Canonical Markdown IR (Phase 4)

Run `python knowledge/tools/build_ir.py --output /tmp/ownkb-ir.json` from the repository root. The output is an internal deterministic JSON snapshot, not a published artifact. The Python driver verifies a closed manifest for the complete canonical tree, invokes the Phase 3 privacy gate in memory, then hands only prepared, sanitized records to the single structural parser (`parse_markdown.mjs`). It requires Node.js and the locally bundled Marked 17.0.5 parser. The vendored parser is distributed under its accompanying MIT license; no network or model is used.

The IR holds documents, hierarchical sections, ordered semantic blocks (paragraphs, lists, tables, code, quotes, rules), inline structure, links, block cue annotations, namespace context, provenance location, and publishable privacy metadata. Cue terms are lexical evidence for later review, not independently extracted atomic claims or a declaration that a proposition applies. Unsupported block/inline tokens and raw HTML fail the build. A new or stale identity fails until a curator updates the committed mapping. The document and section IDs remain stable across path or heading changes when mapping keys are updated with their old IDs. No claim, chunk, reference registry, LLM corpus, or manifest renderer is implemented in this phase.

`guides/` is identified by its directory, excluded before privacy preparation and IR parsing, and checked separately for candidate guide-only factual sentences. The emitted remediation hints contain only path, line, and status. Review each flag against canonical prose before a release. Their heuristic cannot prove absence of guide-only facts.

Accepted Device definitions are integrated incrementally through the closed `device-sources.json` inventory. Pending definitions are excluded; integrated definitions must retain all eight completed review checks in the current Device queue. Their original paths remain provenance paths, while their semantic area is the existing `device-model` area. All four output families consume these same prepared documents. Category/index pages and review logs do not enter this source topology.

The explicit Device identity allocator appends above current mappings and lifecycle history, including retired IDs; routine builds never allocate. Device claim reviews pin exact source-unit keys and blocks, and the unit ledger conserves complete table cells, headers and governing prose. This avoids selecting the wrong repeated table with a lexical similarity heuristic. Canonical source provenance uses the first substantive section when a title-only section has no retrieval chunk; the source title remains the document title.

Tests: `python -m unittest discover -s knowledge/tests -v` and `python -m unittest discover -s knowledge/tools -p test_schema.py -v`. Run the command twice and compare bytes for the complete-tree determinism gate. The final publication scanner remains `python knowledge/tools/validate_privacy.py` and must run on generated artifact families when those exist.
