# Curated IR inputs

`canonical-sources.jsonl` is the closed classification list for every Markdown page in the eight canonical documentation areas plus explicitly integrated, accepted Device definitions. It deliberately contains no `guides/` entries. The source gate rejects a newly added canonical page until it is classified here. A `sanitize` entry is reviewed source policy, not permission to include raw private material. Private captures, logs, inventories, and exports never belong in this manifest as publishable inputs.

`identities.json` maps each canonical path and heading anchor to a durable document or section ID. Its initial allocation was reviewed and committed once. On a move or heading rename, update the mapping key while retaining its ID. Never run `--bootstrap-identities` in routine builds. If a section changes meaning, curate a new identity and retain lifecycle history. OpenWebNet Machine KB 0.1.0 establishes the first public ID compatibility baseline; the registry's `first_release` metadata records that lifecycle origin.

`reference-records.json` is the reviewed semantic input for canonical namespaces, glossary terms, entities, relationships, cautions, open questions, and selected public evidence sources. It stores stable IDs and canonical section IDs, not copied source paths or independent source documents. The build resolves those sections through the shared IR, inherits their public or sanitized privacy metadata, generates record provenance, and fails if a referenced section no longer exists. Canonical-document source records are generated directly from the IR and are not duplicated in this input.

`claim-records.json` contains reviewed assertions and opaque claim IDs. Each claim records its subject entity, namespace, exact section ID and pinned prepared-section SHA-256, evidence class and public source where applicable, status, scope, value, cautions, questions, and typed claim links. To revise a section, review its affected assertions against the new source before updating the digest; never refresh all pins automatically as a routine build step. The generator joins the seed to the same IR used by all other artifacts and rejects stale sections, missing references, and asymmetric contradictions.

`claim-coverage.json` accounts for every section in the bounded canonical claim domains as either claimed or explicitly reviewed non-claim material. The build rejects stale or inconsistent coverage.

`device-sources.json` is a closed inventory of all Device definitions, including those still pending KB integration. Only `integrated` entries enter the shared IR, and each must have an accepted eight-check review in the current work queue. Category pages, indexes and review logs are excluded. Device definitions use the existing semantic `device-model` area and namespace, preserving their original `devices/definitions/` provenance paths. Device-model coverage includes these pages. This adds content under the unchanged public 0.1.0 schemas; no enum or closed schema property is added.

`device-unit-review.json` records dispositions for every prepared paragraph, nested list item, code block and table row of each integrated Device. Row fingerprints include headers and every cell. Section fingerprints also preserve parent headings and firmware/Object context. Each claimed unit maps to claims in the same section; non-claim units require an explicit reason. Changed headers, omitted rows, unmapped claims, dropped cell values/qualifications and stale source pins fail the build. Claims retain the `reviewed-device-pilot` internal review status independently of the earlier Phase 16 review. Their atomicity and evidence contexts must name the same exact source unit as this ledger, rather than relying on the earlier lexical block-matching heuristic.

`device-supplements.json` pins the already public, accepted package-character appendix explicitly linked by a selected Device page. The narrow adapter accepts only `devices/inventory/touch-screen-package-unicode-ranges.json`, its reviewed catalogue provenance, the five fixed package sets and the complete 4,534 numeric/hexadecimal associations. It rejects arbitrary inventory imports, altered bytes, private/free-text metadata and invalid or incomplete associations. It renders named supplementary sections before ordinary privacy preparation and parsing; every prepared row still needs its own reviewed disposition, claim and exact source-unit key. The generated provenance paragraph identifies the appendix path and fingerprints, distinguishing supplemental row provenance from original Device Markdown lines. Explicit review and new section/chunk identity allocation precede any pin change. Package characters do not define identity/network masks, prove installed support or claim examined package payloads.

Run `python3 knowledge/tools/allocate_device_identities.py` only as an explicit reviewed contributor action after selecting and classifying new accepted Device pages. It appends document and chunk IDs above both current mappings and lifecycle history, and refuses to alter any existing document/heading mapping. Review new section identities before curating references, claims, source-unit dispositions and lifecycle entries. Routine builds never allocate IDs or refresh claim pins. The initial compatibility-origin metadata remains 0.1.0; candidate additions are not a new tagged release. Independent semantic certification is still required before release.

The guide remediation check emits path and line only, without copying guide text or adding it to the IR. Release-readiness review adjudicated the current 183 hints with no additional canonical promotion required. Rerun and adjudicate the queue after future guide changes; heuristic flags can include false positives, and an empty hint list does not certify complete coverage.
