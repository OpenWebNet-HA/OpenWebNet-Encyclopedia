## Repeat/restart, panic and prior firmware reconciliation

TMP_SCENARI schema has PK ID_SCENARIO and fields SCEN_NAME, USER_DESCRIPTION, REPEAT, RESTART, SPT_PATH. All24 TMP tables are empty in this manufacturer resource, including scenario/Start/OnlyIf/Action/Panic tables. Therefore these fields show available storage concepts, **not configured scenarios, enabled defaults, working restart behavior or a generated SPT path**. No default value for REPEAT/RESTART is invented from an empty schema.

The existing manual reconciliation documents explicit repeat/restart options, configured panic blocking until power cycle and completed/delayed action qualifications. The prior firmware report functional/run2 independently identified `$RESTART=SI` as a saved-running restoration condition and a configured panic-frame→gate set1→stop iteration. Lifecycle/run17 retained the unresolved gate-clear policy and explicitly rejected an absence/reset inference from its bounded query. The database's panic label/eligibility does not resolve that runtime reset gap or prove the power-cycle behavior.

Prior SLEEP source evidence in functional/run4 has selected m/h/ms conversion/delegate paths, while functional/run5's CHKTIME compares selected local hour/minute and functional/run9's CHKDATE uses UTC calendar fields under their libc/provider premises. Functional/run10 showed numeric time/date results are not automatically Boolean OnlyIf semantics. The new database timing/calendar labels corroborate the documented feature categories; **no source join links these exact database form values to the original emitted helper arguments or a full `.spt` compiler**. No claim equates calendar label strings, wildcards, timezone/DST/astronomical controls with actual deployed scheduling.
