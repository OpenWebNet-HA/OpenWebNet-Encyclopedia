# MHCatalogue firmware, build and resource composition

The catalogue packaged in MyHOMEServer1 `3.87.13` preserves an unchanged firmware-related subgraph from the Suite catalogue, removes many other definitions, and adds eight definitions of its own. It is therefore **not a literal subset** of MyHOME Suite `3.5.38` and cannot be described simply as an older or newer revision. This report establishes stored metadata and relationships, not runtime device admission or installed firmware support.

[schema-and-queries.json](schema-and-queries.json) records every selected table definition, column, index and declared foreign key, plus exact data SQL. Most relationships here are observed endpoint joins rather than declared foreign keys; `AS_CONNECTION_FIRMWARE` explicitly declares its two endpoint foreign keys. [relationship-audit.json](relationship-audit.json) checks fourteen named endpoint relationships in both inputs, finding zero dangling non-NULL references within those checks. That is a scoped integrity result, not validation of the entire database or runtime use.

The product descriptions used only for applicability are frozen under [references-v1](references-v1/REFERENCE_INDEX.json). These are reference-page snapshots, not newly verified manuals. All seven added builds have `localization_level=0`. Item 533 is itself absent from Suite; the parent's device comparison owns its commercial identities. Each of the other seven items exists in Suite, but the added firmware has a distinct item/V/R tuple from its Suite alternatives. Neither database has duplicate item/V/R tuples in this snapshot; the schema does not declare that tuple unique.

The same existing items also retain their Suite firmware records unchanged. Examples: 2205→743 (`1.0`), 2208→746 (`1.0`), 2233→764 (`1.0`), 2237→767 (`1.0`), 2272→803 (`1.0`), 2273→804 (`1.0`), and 2268→801 (`2.0`). Embedded status counts are 114 Official, 7 Prototype and 1 RC; Suite has 289 Official and 22 Deprecated. Hence the 197 omitted Suite definitions include 175 Official records as well as 22 Deprecated records. A universal “discard only deprecated firmware” policy does not explain this data. Negative values in 321 remain literal metadata; no wildcard/version acceptance interpretation is established. `FW_default` and `slots` are stored fields; the runtime selection and capacity policies using them were not traced.

There are 18 embedded and 19 Suite firmware definitions without an `EN_BUILDS` row, including 17 shared owners. No-row cases therefore predate the added 798 and are not evidence of corruption or unsupported versions.

## Configuration, packages and commissioning resources

The configuration-mode lookup is identical, but its numeric namespaces differ: association key 1 means Virtual Configuration with `config_mode=1`; key 2 means Advanced Configuration with code 2; key 3 means Physical configuration with **code 0**; key 4 means Product Programming with **code 3**. Do not equate mode ID 3 with mode code 3.

The 17 added associations are: 321→keys 1/3; 798,844,849→key 2 each; and 850,851,852,853→keys 1/2/3 each. The shared 114-owner graph has no mode-association revision. Product Programming key 4 appears three times embedded versus 167 times Suite, but this follows owner omission rather than stripping that key from retained owners. Exact rows and lookup labels are in [resources-and-associations.json](resources-and-associations.json).

All 50 `EN_PACKAGE` records and all 148 language-package rows are identical in full despite zero embedded `AS_FW_PACKAGE` rows. Package metadata therefore remains as a separately populated catalogue area. Its `GL`, version/release/build and Unicode-set keys are not firmware V/R/B fields or proof of a downloadable payload. Package names are preserved exactly, including inconsistent-looking strings; no normalization or repair is applied. This work does not equate these records with firmware manifest extra resources such as `80/81/94/95.xtz`.

The embedded parameter set is small and retained exactly: all 23 parameter rows and all 23 firmware/parameter/brand/line associations occur unchanged in Suite. They belong only to firmware 23, 110 and 122. Types 1,2,4,5,6 each contribute three resource-path rows; type 7 contributes eight external-software reference rows. These include SDC/SVM/Extra/Director/Protocol resource paths for item 1678 and software names for the other two owners. The brand and line association fields remain independent keys. Paths are reference strings only: the contents, presence, invocation and successful consumption of those resources were not established here.

The two embedded connection associations also match Suite exactly: firmware 23→connection 1 (Serial), firmware 110→connection 3 (USB). The lookup additionally contains Ethernet and Ethernet over USB. Missing association rows do not establish that Ethernet or any other commissioning route is unavailable at runtime.

[canonical-products.json](canonical-products.json) records the exact selected item/commercial identity rows, firmware rows and all five relation bags; it omits opaque commercial visibility expressions. The embedded catalogue's lack of its own server definition is an especially clear reason not to treat this catalogue as a complete self-description or universal support list. It does **not** prove the server cannot control any omitted device. Eligibility may depend on other data/consumers; that policy is not established by these joins.

The Suite F454 and MH202 rows do not identify the actual examined packages `2.0.51` and `1.0.24`, and the server rows do not identify `3.87.13`. The product snapshots already separate those catalogue and package identities (MH202 lines 17 and 101; MyHOMEServer1 lines 395–427 distinguish later published versions). A consumer's range/fallback policy would be required to bridge those specific versions; it was not investigated here. No F454 alarm port, MH202 scheduler, app workflow or physical feature was imported into the server from matching catalogue vocabulary.

## Confidence, unresolved questions and reproduction

High confidence: byte identities, selected schemas/keys, complete selected row-bag differences, shared-owner graph equality, eight new definitions and their lookup/build/mode context, canonical item presence/absence, and fourteen scoped endpoint checks. Interpretation as selective retention plus additions is supported for this subgraph. Purpose, runtime acceptance, active default choice, version-range selection, deployment chronology, installed package/resource use and physical capability remain unresolved.

Useful next questions are the actual matrix catalogue reader's device/firmware eligibility and fallback rules; whether build-less definitions are intentionally handled as such; how mode IDs/default/slots enter that consumer; and which separate consumers use retained package/language/resource metadata. These would be new source investigations, not consequences of missing association rows. No full compiler, configuration parser or runtime policy is claimed.
