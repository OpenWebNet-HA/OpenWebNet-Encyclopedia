## Pointer transfer and object identities

Both selected branches derive r5=scene-owner+24 (0x31432/0x31482), retain the new object pointer in a local slot at stack+80, and call0x30c8c with r0=r5, r1=&that slot (0x31450/0x314a0). On the inspected capacity-available branch,0x30c8c reads the vector end/capacity, writes the object pointer to the old end at0x30c9a, clears the source slot at0x30c9e and updates end at0x30ca0. Its capacity-full branch tailcalls0x30bc4 and is a retained unexamined delegate. Common cleanup0x30e34 only destroys the local pointer when nonzero; the selected normal transfer leaves that slot zero.

This closes the construction-to-action-vector ownership join under the stated normal/capacity premises. It does not establish global destruction/lifetime correctness, runner invocation, actual side effects or capacity-reallocation semantics. The scene owner+24 action vector and action-object enum+28 are distinct from the runner trigger-vector+0 and trigger-element+32 axes being investigated separately. Equal numeric offsets or enum indices cannot join those different objects.
