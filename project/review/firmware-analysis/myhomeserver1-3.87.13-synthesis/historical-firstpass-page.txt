## Application structure

The normal image contains 5924 regular files, including 858 ELF objects; recovery contains 5384 regular files and 740 ELF objects. Among 5378 shared regular paths, 5368 have identical bytes and ten differ. The normal image has 546 unique regular paths and recovery has six. These counts describe retained files, not semantic coverage or runtime equivalence.

Selected applications include `matrix_mx`, `scheduling_manager`, `alarm_manager`, `backup_manager`, `gateway_manager`, `energy_manager`, `player_manager` and `bt_smart_home_manager`. They sit outside the older `bin` directory. Their original ELF dependencies and selected JSON key structures are retained in the [structural report](../../project/review/firmware-analysis/myhomeserver1-3.87.13/inventory-report.txt). An application name alone does not prove ownership of an entire product function.

The selected modern applications and the 44 inspected core/provider objects use ARM32 EABI5 hard-float. `matrix_mx` is a Thumb-entry PIE with the ARM hard-float interpreter. This requires fresh calling conventions and object layouts; earlier firmware harnesses cannot be transferred by filename.

## Startup and configured ownership

Original SysVinit metadata selects runlevel5 and the vendor startup script. The normal script sets the library search path, changes directory to the vendor application root and requests `bin/bt_daemon` without explicit arguments. A user-library directory precedes packaged providers. Original daemon code reaches a default stack path, markup parsing and process-field stores; live lookup order and successful startup remain separate questions.

The normal and recovery `stack_open.xml` files are identical and declare 25 processes, including the modern managers. The `working_mode` text callback stores record offset8. The inspected launch helper skips zero-mode records only under its selected global status2 predicate, while the packaged `normal_status` literal is4. These values must not inherit the older firmware's mode semantics. The selected eligible-record path builds a `nice` command and calls a child-launch helper; it is not an observed process launch.

## Separate OPEN implementations

The selected `bt_device` dependency family includes the C++ `libopen`/`libdiag`/`libwhere` providers. `openserver` and COSO instead directly declare the C `libopenmsg` family. Repeated C++ bridge/parser symbols also occur in `libcommon`; declarations and definitions do not establish the actual dynamic lookup result.

In this build's `usr/lib/libopenmsg.so.1.0.0`, SHA-256 `8d1ac556922c280688b0e424737682d9ec2caa83b6783b621677fcdba153c8e1`, original `new_open_msg` instructions at `0x3a24..0x3a78` request a zeroed 56-byte object and initialize the discriminator at offset52. The selected ordinary parser branch writes discriminator1 at `0x3c28..0x3c32`. This differs from the MH202 pointer parser's 48-byte object and discriminator44. It is static source evidence, not a successful parser experiment or a shared C++ layout.

Actual auxiliary and automation plugin initialization reaches registration stores and descriptor callback relocations. Auxiliary criteria contain9 in both directional lists; automation has separate reverse criterion1 and forward criterion2. Numeric criteria, WHO, parser kinds, envelope representation and callback direction are distinct namespaces. Selected original auxiliary code supplies the four-byte body construction and separate reverse WHO9 formatter recorded in the [protocol report](../../project/review/firmware-analysis/myhomeserver1-3.87.13/protocol-report.txt). The two host examples are synthetic and do not form an observed roundtrip.

The complete seven-file `libcoso` directory enumeration contains the core, SCS, debug, auxiliary TR/STM and automation TR/STM files. Other descriptor names exported by a file do not establish an implementation or registration for those features. This directory scope does not locate the product's scenario implementation.

## Evidence limits and next investigations

The first pass establishes original composition, selected startup/registration code, parser allocation changes and a distinct catalogue. Exact source reports and independently checked identities are retained in the review capsule. Whole-process execution, live binding, configured state, delivery, persistence, electrical topology, timer scheduling and physical effects remain unproved. Manufacturer signature blobs were retained but their cryptographic verification is not established. Referenced extras `80.xtz`, `81.xtz`, `94.xtz` and `95.xtz` are absent from this download.

The next useful work is narrowly scoped:

1. Trace `matrix_mx` from the catalogue literal through path construction, opening and selected queries; compare meaningful changed catalogue records without assuming stable IDs.
2. Trace `scheduling_manager` scenario storage, trigger/action schema and lifecycle, then its actual command handoff. Do not substitute the MH202 script engine.
3. Close one fresh COSO parser/provider/outer-dispatch-to-STM path before attempting bounded original execution.
4. Establish `alarm_manager` provider/bus ownership and the backup/persistence contract from actual consumers. Do not inherit F454 alarm wiring or AV roles.

Broader Device review gates remain pending. This first pass does not change published command semantics or claim complete firmware coverage. Earlier stopped authentication/session/framing investigations remain closed.
