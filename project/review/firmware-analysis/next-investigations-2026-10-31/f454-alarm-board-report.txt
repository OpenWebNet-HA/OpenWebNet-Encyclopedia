# F454 alarm lane: kernel board records and unresolved connector wiring

This batch adds original kernel evidence beneath the previously established alarm pathname `/dev/ttyS2`. The original filesystem node is character device **major4/minor66**, matching index2 in the packaged `ttyS` driver whose base minor is64. The kernel contains **two DM365 serial records and a separate BASI board serial record**. Its ordinary selected board code requests registration of the DM365 serial device before registering the separate BASI serial device. Under successful compatible driver initialization and the stated slot-state premises, the latter can occupy the third serial slot. This is stronger than a pathname/name match, but it does **not** close the electrical connection to the documented SCS AI terminal.

In particular, `/dev/ttyS2` must not be restated as “DM365 UART2.” The selected DM365 platform table has two nonterminating records, at address words `0x01c20000` and `0x01d06000`. The separate BASI record has address word `0x04000000`, interrupt65 and clock8000000. The actual connector, transceiver, external logic and pin wiring behind that separate address remain unknown here. Neither an XML bus_type nor a Linux ordinal supplies those facts.

## Initialization, pinmux and index allocation boundaries

Within the selected BASI code, `0xc000efdc..0xc000eff0` requests pinmux entries36 and37, loads the configuration pointer whose enabled mask is7, and calls `davinci_serial_init`. That helper walks **two** DM365 records, checks the supplied mask where applicable, obtains clocks and requests `platform_device_register(dm365_serial_device)` at `0xc000daf4`. Its register/clock operations are inspected as code only, never performed.

Later, `basi_init:0xc000f230..0xc000f234` loads literal pool `0xc000f384→basi_dm365_serial_device` and requests `platform_device_register`. The earlier call at `0xc000efd8` is **not** this registration: its literal is a LED-device pointer. This pre-output distinction was resolved by original operands; no generated candidate was overwritten.

The original `dm365_pins` table at `0xc02986ac`, indexed in16-byte records by `davinci_cfg_reg`, names entries36/37 **UART1_RXD_34** and **UART1_TXD_25**. Their table configuration bytes are respectively `[16,14,3,3]` and `[12,29,3,3]`; the selected register-update code uses the byte fields as register offset/shift/mask/value. The suffixes34/25 are retained as **literal table labels**, not interpreted as package-ball, PCB-header or connector pin numbers. These entries relate the selected DM365 UART1 pinmux request to named SoC mux records; they do not establish the separate BASI serial record's connector wiring. No actual register values or pin voltage was read.

`serial8250_register_port:0xc0187280..0xc0187330` first searches existing ports with `uart_match_port`, then searches for a slot with type+112 and I/O-base+0 both zero; another fallback can choose an untyped slot. It copies the selected port fields and calls `uart_add_one_port`; on its success it returns that slot's line word+124 at `0xc0187420`. `serial8250_isa_init_ports` initializes line ordinals, with200-byte port records. Therefore the BASI platform ID or table index does not force a particular tty ordinal.

The finite host ledger states the sufficient limited premise: if normal DM365 records occupy typed slots0/1, no earlier match/other registration or override changes them, slot2 is available, and the BASI probe/registration succeeds, the distinct BASI record selects slot2, corresponding to the packaged tty prefix/base-minor and node major4/minor66. This is a conditional source composition, **not** a captured initialization order, proof of all clock/registration outcomes, dynamic major/minor observation, or complete kernel boot. The raw ordered registration requests support this possibility; the unobserved probe/slot state remains material.

## Product terminal and remaining attribution gap

The frozen reviewed device0002 page documents SCS AV and SCS AI terminal labels from `MQ00519-c-EN`, printed p499/PDF p1, and distinguishes their A/V/automation and burglar-alarm roles. This pass uses that existing reviewed synthesis; it does not re-extract a primary schematic/PDF or assert a schematic is globally unavailable. The selected kernel and packaged metadata provide no demonstrated net/connector relationship between the BASI serial record at `0x04000000` and that SCS AI terminal. They also do not identify a particular transceiver or explain the hardware behind interrupt65.

High confidence: original image character-node identifiers; recovered target/configuration and symbol/table identities; concrete BASI/DM365 register-request operands; distinct record data; selected driver copies, mux labels and slot-selection code. Conditional: machine/driver activation, matching/provider success, normal-record typed allocation and third-slot assignment. Unresolved: actual ttyS2 runtime backing and, beyond that, electrical topology to the documented terminal and natural alarm event origin.

The next decisive evidence would be a BASI circuit/net map or an independently established board-driver resource description linking address `0x04000000`/interrupt65 to the alarm interface and its connector. That work does not require reopening the excluded connection/auth/session/framing paths. Names, default ports, configured bus_type and a synthetic alarm frame are insufficient substitutes.
