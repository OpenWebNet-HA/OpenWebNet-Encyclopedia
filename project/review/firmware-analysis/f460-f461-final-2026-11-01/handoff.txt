# F460 and F461 firmware knowledge handoff

F460 2.0.12 and F461 2.0.11 share substantial packaged material, but their selected implementations and documented product roles remain distinct. This study connects catalogue selection, scene processing and update staging in F460, and configuration, module management and selected translation paths in F461. It establishes conditional software contracts for these exact builds. It does not establish installed configuration, successful delivery, measured timing, safe concurrent lifetime or physical operation.

The [detailed analysis](f460-f461-deep-analysis.md) supplies the build-specific claims and original evidence. The [package comparison](f460-2.0.12-and-f461-2.0.11.md) and [first source-path study](f460-f461-selected-source-paths.md) cover the starting material. The [final review capsule](../../project/review/firmware-analysis/f460-f461-final-2026-11-01/README.md) separates source reviews, documentary review, saved validation and the navigation catalogue. Fifteen checkpoint rows describe navigation, not a percentage of the firmware examined or a new semantic review of every indexed file.

### F460: catalogue parameters belong to a supplied owner

The selected catalogue path is more than a database filename. Original code connects a SQL template, concrete constructor and reader. A callable registry and adapter explain how the higher caller selects key89 and forwards three values from the same supplied owner into the constructor's `modobj`, `line_modobj` and `brand_modobj` placeholder roles. Key89 supplies a separate query/class key; it is not a Device identifier or WHO number. The reader requests columns13 and14 as text for slots and system ID. [Catalogue and selector evidence](../../project/review/firmware-analysis/f460-f461-run05-2026-11-01/README.md) builds on the [opening and reader evidence](../../project/review/firmware-analysis/f460-f461-run04-2026-11-01/README.md).

Tooling should preserve database generation, owner and query-key namespaces separately. The [catalogue profiles](../../internals/mhcatalogue-source-profiles.md#additional-f460f461-profile-and-selected-f460-consumer) retain the shared F46 database profile and the distinct earlier MHS/Suite comparison. The selected F460 reader permits repeated rows to overwrite destination fields; a first-row or null-text guard was not found in that bounded path. This is a local source limit, not a demonstrated runtime defect. Root owner construction, actual supplied values, complete row selection/fallback and successful string, filesystem and SQLite providers remain open.

### F460: a scene request is several separate contracts

One construction path identifies an in-place SceneRunner and connects it to the initializer receiver later captured as a raw pointer. A selected local entry requests thread state, thread start and detach. The worker consumes eight-byte condition pointers; selected actions use sixteen-byte pointer/control pairs. These joins establish one owner context and request path, not an owning callback capture, successful thread or safe lifetime. [Receiver and worker evidence](../../project/review/firmware-analysis/f460-f461-run07-2026-11-01/README.md) keeps these boundaries explicit.

The selected BNIL trigger has its own raw/compiled state and method/ID admission path. The BNCUSCENE condition's entire short predicate reads its enabled byte and XORs one; its local body contains no target-scene lookup. The selected BNLD condition compares a configured signed threshold with a supplied record integer under enabled, valid-record, exact status and selector premises. Its actual raw serializer and operator parser support a narrower constructor-reachable value route under ordinary fresh JSON, member/string/move/int/asInt providers and unchanged objects. This is not a universal JSON roundtrip, public operator grammar, physical unit or configured condition. [Trigger](../../project/review/firmware-analysis/f460-f461-run06-2026-11-01/README.md), [scalar condition](../../project/review/firmware-analysis/f460-f461-run09-2026-11-01/README.md), [numeric predicate](../../project/review/firmware-analysis/f460-f461-run14-2026-11-01/README.md) and [selected serializer](../../project/review/firmware-analysis/f460-f461-run15-2026-11-01/README.md) reports retain their own layouts and evidence.

The selected SLEEP callable forms a wait request whose seconds interpretation is conditional on the ordinary Linux LP64 API/ABI. Its completion byte can be set after a normal callback return that followed a non-retry wait error. Later action polling can also reach cleanup after a separate scene flag becomes nonzero, without a fresh true completion-marker read. Therefore neither marker nor cleanup proves that every action completed or that a delay elapsed. A separate positive local flag writer remains unjoined to a natural caller and receiver class. [Wait/completion](../../project/review/firmware-analysis/f460-f461-run03-2026-11-01/README.md), [dispatch/poll](../../project/review/firmware-analysis/f460-f461-run10-2026-11-01/README.md) and [unresolved writer context](../../project/review/firmware-analysis/f460-f461-run11-2026-11-01/README.md) are distinct contracts.

### F461: configuration and module requests are connected locally

Actual main-option and key-file paths explain which supplied library/configuration directories reach the module manager. Nonnull option-produced pointers take precedence over the selected key reads; missing configuration-directory input has a separate parent-directory fallback. The local loader checks names and both required symbols, retains a path/handle entry, then requests initialization. A successful traversal return can include skipped or failed entries; it does not certify that any module initialized. These are source selection rules, not observed command-line arguments, current working directory, active settings or installed modules. [Configuration selection](../../project/review/firmware-analysis/f460-f461-run11-2026-11-01/README.md) and [module admission](../../project/review/firmware-analysis/f460-f461-run14-2026-11-01/README.md) retain the separate pointer-holder and directory-object roles.

The later monitor registration passes the same manager as callback data. Under ordinary event ABI, valid retained objects and normal providers, one numeric event and file-path suffix match reach a conditional stop lookup/call followed by list/head bookkeeping, path free, handle-close request and entry free. This establishes local request order, not actual stopping, completed unloading or safe concurrent lifetime. GModule and plugin stop bodies remain opaque. [Removal evidence](../../project/review/firmware-analysis/f460-f461-run15-2026-11-01/README.md) also distinguishes a path load before the head store from the later free call.

## Evidence levels and reproduction

This dual study added no original F460/F461 firmware, native helper, target process, provider, operating-system service, network, bus or physical execution. Static host extraction, identity checks and the initial host SQLite comparison are different activities. They do not demonstrate target SQL behavior. Later source collectors and final navigation check saved bytes and selected source guards; they do not execute the vendor instructions or semantic test fixtures.

The earlier MyHOMEServer1 experiment remains separate: one saved corpus, eight top-level entries, 340 original code-hook visits, zero C primitives, twelve definition redirects, eight private EXIT boundaries, zero guard stops and 360 total hooks. Four data-relocation setups and the recorded host register writes remain separate. It tested four supplied finite double-constructor/SAME-object-asDouble cases. It supplies no F46 integer/JSON/runtime evidence. F454 and MH202 ledgers remain separate, with no replay accumulation; unavailable MH202 run18/run21 intermediate drafts remain unverified.

The final navigation catalogue checks selected saved documentary identities and exact captured inputs. It does not independently verify every member of every historical index, re-audit all source semantics or reopen completed collectors. Saved passes remain observations of their recorded versions. When a later documentary edit changes a Device or overview page, historical reproduction needs the exact retained input bytes. Refined reports and older canonical collector report pins are listed separately; broad similar-file fallback and silent repinning are not valid reproduction.

## Next concrete investigations

1. **Configured objects and natural callers:** establish actual scene/key-list construction and the unresolved F460 local writer receiver/caller; for F461 establish selected module instances, natural records and effective settings. Keep private object roles separate from public capabilities.
2. **Provider and record correlation:** qualify query type, ID, freshness and unchanged lifetime; locate a permitted positive producer of F461 nonzero deadline32 and establish its clock coordinate. Complete JSON/XML/SQL behavior requires its own evidence.
3. **Ownership and lifecycle:** connect natural last-owner, worker/poll/removal and module teardown ordering, including failures, exceptions and concurrency. Local free/close/detach requests are insufficient.
4. **Platform and installation:** qualify actual nonsecret boot/DTB/auxiliary-core selection and updater context/order through permitted source paths. Compatibility, trust and installation outcomes require separate evidence.
5. **Runtime and physical corroboration:** use identified hardware/configuration and explicit observation scope for timing, delivered traffic and effects. Source predicates and formatted strings cannot supply those observations.

These are remaining questions, not a claim of exhaustive coverage. Closed receiving, output, transport, authentication, session, framing, MQTT/libjel and excluded process/command routes remain closed. The separate Device dossiers retain their manual/catalogue review scope; this build study does not confer full Device, source, runtime or physical approval.
