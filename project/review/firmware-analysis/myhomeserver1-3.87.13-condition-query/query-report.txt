# BNLD local record query: immediate cache return and conditional wait

The BNLD predicate's query `0x10f4a0` first invokes the ordinary local lookup `0x10e3d8`. On a nonnull returned data pointer, it copies the exact record/control pair to its caller's output and returns normally **before examining the query selector or the record discriminator**. A cached record is therefore not locally revalidated for type or refreshed by that selected fast path. This is a bounded source fact, not a claim that the installed cache contains an unsuitable or stale object.

A miss takes a different path. The caller's selector zero reaches a local request-preparation branch and opaque call boundaries. Its normal post-delegate continuation reaches a local mutex/condition-variable wait that tests a response-string length. These relationships do not establish successful request delivery, a fresh response, a particular reconstructed record type, measured waiting time, or a valid physical value.

## Conditional local waiting dependency

The common local continuation forms **registry+72** and requests `pthread_mutex_lock`. A nonzero return branches to the error delegate at `0x110e08`, outside this bounded normal-path analysis. This registry mutex address is unrelated to the shared action-stop domain's offset-72 flag: different receiver and namespace.

After a zero lock return, `0x10f582` requests `steady_clock::now`. The source builds an absolute comparison deadline by adding the original 64-bit literal **`0x00000002540be400` = 10,000,000,000** to that returned count (`0x10f588..0x10f598`). This packet records source counts only; it does not newly prove provider tick units, kernel clock ABI, elapsed time, scheduling or a wall-clock bound.

The immediate test at `0x10f59c` reads **registry+100**, the response-string length. A nonzero value skips the wait into `0x10f6b4`. No condition-variable or clock provider body is executed or expanded.
