## Selected auxiliary route: exact local bodies

`aux_tr_translate` at `0x18d4..0x1928` selects `aux_tr_scs2open` only for numeric callback axes `(r0,r1)=(1,2)` and `aux_tr_open2scs` only for `(2,1)`; other pairs return without invoking these branches. Those numbers are callback direction/representation axes, not WHO1/WHO2. The source input envelope is another object from the parsed object. Here envelope+56 selects representation2 or3, and the parsed object's+52 discriminator is separate. Their shared numeric values must not be conflated.

For the selected forward branch (`0x16fc..0x18c8`):

- Envelope representation3 supplies an already parsed pointer at+0. Representation2 instead calls original `buf_to_openmsg` at `0x17dc`, frees the former ASCII buffer, and replaces envelope+0/+56 with the parser result and literal3. Parser return/acceptance is not supplied by this analysis.
- Parsed discriminator must equal1 at `0x1734..0x1740`. Decimal conversion of field+8 and field+16 occurs at `0x1758..0x1774`. These are the selected WHAT/WHERE text slots used by this local plain-command route; base-field/parameter parsing is not flattened into proof for arbitrary complex fields.
- A switch on converted field+8 values0..10 chooses the two trailing bytes; `0x1730..0x1738` initializes first bytes `b0 00`. At `0x1804` the selected low-nibble code is ORed with converted field+16 shifted left4. The routine converts four bytes to ASCII through `array_to_ascii_hex_frame`, then calls `prepare_briefscs_frames` with criterion9 at `0x1830..0x1844`. This is a local helper handoff, not serial framing, publication or actuation.

`HOST_RECONSTRUCTIONS.v1.json` records **postparsed synthetic** WHAT text`3`, WHERE text`5`, discriminator1, envelope representation3 and successful normal decimal conversions. Source switch entry for3 leads to `0x1878`, selecting `9b/0`; the composed four bytes are `b0 00 9b 50`, hence ASCII body`B0009B50`. No original parser, body builder or helper executed for this example. No bounds/validation claim is made for other decimal strings.

For the independently selected reverse branch (`0x1568..0x16f4`), envelope type at+40 must be3 or9. It converts eight ASCII hex characters, requires first byte high nibble`b`, and switches on byte2 `9a`, `9b` or `9c` and byte3's low nibble. The chosen WHAT and byte3's high nibble are passed to safe literal`*9*%d*%d##`. Original PIC arithmetic at `0x1644` plus pool word`0x69c` at `0x16f8` resolves the format at VA`0x1ce8`. `scsmsg_to_openlist` is then called with criterion9 (`0x164c..0x1658`).

The separate synthetic ASCII body`B0009C52` selects WHAT7 at `0x16b0`, WHERE5 from the high nibble, and constructed candidate`*9*7*5##`. It was not captured from hardware and is not paired with the forward example as an observed roundtrip. `ascii_hex_frame_to_array` and `array_to_ascii_hex_frame` original helper definitions are separately located at instruction VAs`0x3358` and`0x33c0` in `libutils.so.1.1.0`; their selected loops are retained. List construction, downstream serialization, STM admission and socket/bus effects remain outside this pass.

## Packaged configuration and diagnostic identity limits

`CONFIGURATION.v1.json` exports only whitelisted nonsecret fields and process metadata. In `stack_open.xml`, `bt_device` has `scs_enable=1` and `object_model_15_not_managed=1`; `bt_luci` has `disable_automation=1` (exact original line numbers in that output). COSO is listed as a process with numeric working_mode0, whereas `bt_device`, `openserver` and `scsserver` have1. The full startup/working-mode semantics are not inferred here, and these defaults do not establish which processes were active in a device. The coexistence of automation code and the `bt_luci` disable field is retained as distinct scope, not harmonized into global enabled/disabled functionality.

`MANIFEST_IDENTITY.v1.json` pins update XML identity `MyHomeServer1`, firmware`3.87.13`, XML version`3.1`, Object model`5.0.67`. These are package declarations. `libdiag` exports `OPN_OpenScsDiagGenTr::o2s_deviceModel` at`0x9a2d` and `s2o_deviceModel` at`0xf319`, plus distinct Id, Termo, KeyObj and Ppt translator classes. Those definitions are entrypoint inventory only: no model query, translator registration, model/version formatter or diagnostic reply was executed/traced in this batch. In particular `5.0.67` is not a physically corroborated diagnostic identity.

## Reproduction, integrity and coverage

Run from the workspace with host Python only:

```
python3 -B work/myhomeserver1-firmware/3.87.13/research/2026-10-31/protocol/collect_protocol_v1.py --check
```

The collector reads original bytes, host `readelf` and host `objdump -m arm --dwarf=no-follow-links`; it does not load or run any original object. Separate-debug links are explicitly disabled in retained disassembly. Inputs97; selected ELFs44; retained spans10; exact ARM-word/Thumb-halfword guards25; host reconstruction cases2; generated outputs22 including the manifest. Every output comparison uses bytes. Initial generation refuses any existing candidate output; `--check` writes no candidate. `first-candidate/` immediately preserved all22 outputs and the collector,23 exact copies; its index was calculated before opening its own index file. The report is preserved separately on publication. Reviewer documents are deliberately excluded from author manifests to avoid self-hash cycles.

Confidence is high for original identities/headers/declarations, the selected literal registration stores/callback relocations, allocation/discriminator writes and inspected local auxiliary arithmetic. Host examples demonstrate consistency with those selected branches, not original execution. Whole parser acceptance, complete key/WHO/WHERE grammar, provider binding, registry/STM/loader state, publication and physical behavior are unverified.

Highest remaining questions, if later authorized, are: (1) exact original COSO outer criterion/WHO population and dispatch-to-STM handoff for one normal auxiliary or automation route; (2) concrete loader/provider closure for the repeated C++ parser/bridge symbols before any layout-based execution; (3) actual diagnostic factory/key and model formatter route; (4) normal level/interface/group addressing in the fresh `libwhere` implementation. No conclusion here requires inspecting session, authentication or transport framing internals.
