# MyHOMEServer1 3.87.13: catalogue open and row-reader consumer

The packaged `matrix_mx` contains **actual calls opening the exact absolute catalogue path**, not merely an unused filename literal. One local setup helper opens it twice into distinct context fields and reports success to a caller. A separate local reader requests the same file with `sqlite3_open_v2`, prepares an object-supplied SQL string, converts selected result columns and stores them in that object. The producer of that reader's SQL string remains unresolved, so this batch does **not** establish a device/Firmware eligibility rule or assign names to those result fields.

All findings are static compiled requests. No original instructions, vendor processes, SQL statements or stored expressions were executed; no target/network/device operation occurred. Prior firmware/source reports and original image files were read only.

## Separate concrete catalogue row-reader

Local reader entry `0xa8c00` independently reconstructs the **same** absolute path through pool `0xa8d08` plus Thumb PC at `0xa8c20`. It first requests `stat`; only return zero reaches the open request. At `0xa8c3e` it calls `sqlite3_open_v2(path,&stack_handle,1,NULL)`. It requires open return zero and a non-NULL handle before preparing SQL. These are source-level requested flags and guards, not proof of a naturally successful read-only session.

At `0xa8c56..0xa8c60`, the prepared SQL pointer comes directly from `word[input_object+36]`; the remaining request is `sqlite3_prepare_v2(handle,sql,-1,&statement,NULL)`, with return zero required. Its object argument and SQL pointer are **not** borrowed from the setup helper's context. The reader's handle/statement slots are private stack locals, unlike the setup helper's two long-lived context fields.

The selected result path is precise:

1. Initial `sqlite3_step` at `0xa8c64` is compared with literal **101**. That value takes the immediate finalize path. Other initial return values reach the statement-pointer test; the code does not first require literal 100 here. No error-handling defect is inferred from that local fact.
2. With a non-NULL statement, `0xa8c72..0xa8c96` requests `sqlite3_column_text(statement,13)` then `strtol(text,NULL,10)`, storing the result at object offset **20**; column **14** is converted the same way and stored at offset **24**. These are zero-based column argument numbers and object offsets, not known semantic field names or catalogue key values.
3. The subsequent step at `0xa8c9a` repeats this column/store block only when return equals literal **100**. On that normal repeated-row path, later rows overwrite those two object fields. No ordering or single-row guarantee is established because the actual SQL producer is unresolved.
4. Ordinary loop exit requests `sqlite3_finalize`, then reaches a tail call to imported `sqlite3_close`. Immediate initial-101 also finalizes before closing. Prepare failure goes to close without a local finalize call on that edge. Earlier stat/open/non-NULL-handle failures return without a newly assigned uniform Boolean result.

The close tail at `0xa8cc4` targets Thumb veneer `0x108a4`, whose first bytes are `78 47 fd e7`; it interworks to the ARM PLT stub at `0x108a8`. The same logical import is called directly through ARM-interworking branches elsewhere. This avoids confusing a Thumb veneer with a distinct provider or an executed callback.

`100/101` are recorded as the actual code comparisons; conventional SQLite row/done interpretation does not turn other first-step results into observed rows. Finalize/close results are not validated in the selected normal path, and its returned close result is not promoted to a Boolean success contract. NULL column text, conversion failure/range, malformed SQL, application exception behavior and actual row contents were not modeled or tested. No default, credential or configuration value was read from SQLite.

## Concrete item/system SQL declaration: useful, still a separate join

The whitelisted SQL literal at `0x1c4390` is:

```sql
SELECT AS_ITEM_SYSTEM.id_item, AS_ITEM_SYSTEM.id_system FROM AS_ITEM_SYSTEM WHERE AS_ITEM_SYSTEM.main=1
```

The initializer at `0x11138` is an actual stored `.init_array` entry: index 1 of 72 entries, stored Thumb pointer `0x11139`. Its literal-pool arithmetic loads this exact SQL string, and its `0x11168` call requests string construction/copy into linked global address `0x20f024`. The inspected helper at `0x2a140` initializes a string buffer pointer, computes source length, copies data and stores length/NUL; allocation/copy APIs remain delegates.

This positively ties an item-to-main-system SQL declaration to a compiled initializer request. It is **not** joined in this batch to the selected reader's `object+36`, an actual prepare/execute invocation, a row consumer for those two item/system columns, or the caller's eligibility decisions. The selected reader accesses columns 13/14, so silently substituting this two-column query for its unknown SQL would be incorrect. Nor does `.init_array` registration prove startup reached it on a device. This report intentionally keeps those boundaries separate rather than inventing a complete query pipeline.
