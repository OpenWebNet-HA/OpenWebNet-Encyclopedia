## The scenario engine has concrete owners and gates

The [startup analysis](myhomeserver1-3.87.13-startup.md) connects main to a scene container, a time-trigger service and a configured scenes directory under extra0. The selected loader reads candidate JSON files, requests JsonCpp parsing, builds raw trigger/condition/action objects and initializes compiled runners. The downloaded images contain no regular files under that exact scene-directory prefix. This leaves installed configuration unavailable; it does not establish an absent live directory or disabled scenario feature.

```mermaid
flowchart LR
    A[Selected scene JSON] --> B[Raw schema objects]
    B --> C[Serializer and reparse requests]
    C --> D[Compiled scene and objects]
    T[TIME service or selected local event] --> L[Scene callback and launch gates]
    D --> L
    L --> K[Condition predicates]
    K --> W[Action worker]
    W --> P[Completion poll and scene cleanup]
    R[Selected typed local records] --> K
```

The arrows represent selected conditional source relations. They are not a captured transaction. Valid objects, ordinary provider returns, matching IDs/types, configured admission and lifetime remain premises at their respective boundaries.

The [factory](myhomeserver1-3.87.13-factories.md) and [action](myhomeserver1-3.87.13-actions.md) studies distinguish raw JSON-facing objects from compiled callables. Selected SLEEP and SCENARIO paths reach actual constructors and action storage. The nested SCENARIO callable's captured container is connected to the same startup container populated by the loader. Numeric IDs, duplicate-key insertion and one category-specific key allocator are traced; they do not establish a universal external ID grammar or ordering policy.

The scene's enabled and active checks govern selected thread requests. A condition worker calls each compiled condition's predicate slot and stops at the first zero. The all-nonzero or empty-condition path reaches the action worker. Trigger and action vectors contain selected eight-byte pointer/control pairs; the condition range uses four-byte compiled-object pointers. That representation difference does not establish absent condition ownership: a later teardown loop positively calls each nonnull condition's deleting slot before requesting vector-storage deletion.

## Timing, cancellation and lifetime answer different questions

SLEEP's selected callable requests whole seconds under the verified ordinary API layout. The common action wait uses a separately derived operational scale of60 seconds. JSON metadata, operational delay and operational duration must therefore be traced through their own setters; equal field names do not establish equal use. One BN3L construction route positively connects duration to operational+12 and a second callable, while the earlier selected SLEEP route retains duration metadata separately. The [serialization and ownership study](myhomeserver1-3.87.13-serialization.md) preserves these distinctions.

| State or owner | What the selected source establishes |
| --- | --- |
|Scene stop+144 and active+145|Scene cleanup can clear both after leaving a completion poll|
|Action completion+4|A separate per-action value; scene cleanup does not set it or prove worker completion|
|Shared action-domain flag+72|Selected action stop requests set a common cancellation flag; scene-byte clearing is not its reset|
|Thread-state receiver|A raw action/scene pointer; disposal of the small state is separate from receiver lifetime|
|Thread holder|Successful detach can clear its word before worker completion|
|Registry and compiled owners|Concrete retain/release, vector and teardown requests are traced; natural last ownership and concurrent ordering remain open|

The [cancellation](myhomeserver1-3.87.13-cancellation.md) and [lifetime](myhomeserver1-3.87.13-lifetime.md) reports establish these source relations without declaring a race, leak, use-after-free, permanent cancellation latch or successful restart. A selected numeric scene-removal caller clears a stored scene/control pair before requesting release and keyed erasure. Its local ID provenance is traced, but equality between that dispatcher's supplied context and startup's main container remains unresolved. A positive runtime reset owner for the shared action flag is still missing.

## The database has practical value without being a capability oracle

The [complete catalogue comparison](../../internals/mhcatalogue-source-profiles.md) establishes a distinct embedded profile: all75 table definitions match the Suite version, but the complete schema has one additional embedded index;42 table row multisets match and33 differ. Some definitions are retained, others omitted or embedded-only. Reused Configuration IDs and equivalent renumbered fields require owner-aware correspondence. Combining rows by filename or integer ID can assign a field to the wrong product.

The [consumer](myhomeserver1-3.87.13-consumers.md) and [ownership](myhomeserver1-3.87.13-factories.md) continuations add actual compiled opening requests and the selected15-column SQL producer. They identify the selected columns as catalogue slots and system IDs. They do not execute those SQL requests in the firmware or resolve the server's entire device-selection/fallback policy. The embedded catalogue's omission of MyHOMEServer1's own item also prevents treating its contents as a complete self-capability declaration. Canonical archive identities remain separate for the embedded and Suite databases.
