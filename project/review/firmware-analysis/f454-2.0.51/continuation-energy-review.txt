## Material finding

Original `0xe70c` compares row with0x16; unequal reaches`0xe76c`, which compares with **0x19**. Row0x19 alone enters`0xe774–0xe7ec`, obtains `strlen`, sets destination to existing buffer+length at`0xe7e0`, and uses the `*%d*%d*%d` literal at pool`0xe9b0`.

The selected rows0x10/0x14 instead branch at`0xe770` to`0xe7f0`. That path loads the **nonleading-star `%d*%d*%d`** literal via pool`0xe928` at`0xe840`, and sets the destination directly to **context+820 at`0xe850`**, then branches to `sprintf` at`0xdd00`. It **replaces** the persistent text with the current three decimal bytes. It does not preserve or append the earlier two values.

Therefore the selected second record's buffer/parser input must be:

```text
row10: buffer12*13*14 → *#18*51*56#10#2*2*12*13*14##
row14: buffer12*13*14 → *#18*51*510#10*2*12*13*14##
```

The third record temporarily replaces the buffer with`3*15*16`, then the already-correct terminal rule replaces it with`3*15` for row0x10 or`3` for row0x14. Terminal values/frames and the distinction between intermediate/terminal parser/send calls remain valid. Existing critical assertion`0xe7e0` belongs to the **other row0x19** append branch and cannot corroborate selected-row accumulation.
