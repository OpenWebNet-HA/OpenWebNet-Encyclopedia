# F460 2.0.12 and F461 2.0.11 Parallel Firmware First Pass

The two packages share much of their packaged platform and exactly the same embedded catalogue, while their application inventories and selected common binaries differ. Main applications use AArch64, requiring fresh layouts relative to the [ARM32 MyHOMEServer1 examination](myhomeserver1-3.87.13-research-synthesis.md). These are build-specific package/source findings; no firmware process, configured installation or physical bus was executed.

## Reference and product scope

[Curated F460](../../devices/definitions/own-dev-0207-f460-myhome-server.md) is the Home + Project/Home + Control server. [Curated F461](../../devices/definitions/own-dev-0208-f461-myhome-server-third-party-integration.md) serves local third-party control. Shared installation documents and catalogue Objects do not transfer F460 app/alarm behavior or F454 AV/alarm hardware to F461. The [review capsule](../../project/review/firmware-analysis/f460-f461-2026-11-01/README.md) retains separate product reports, independent reviews, comparison code and exact evidence/history.

The normal images share5823 regular paths:5757 have identical complete hashes and66 differ. Eight selected common applications/core programs are present in both, and all eight differ in whole-file bytes. A byte difference does not by itself establish a changed function, while a common name or dependency does not establish identical layout or behavior. The header census also retains minority/other ELF machines; not every packaged object is AArch64.

Both kernel bundles contain an ARM64 Image, six DTBs and a separate hygw_cortex-m.bin payload. The kernel and auxiliary payload hashes differ; all six corresponding DTB payloads match. DTB model/compatible strings are candidate board descriptions, not a physical probe or proof of the DTB actually selected. The kernel banner's anomalous2011 timestamp is not used as release chronology.

Original startup scripts declare auxiliary-core/device-node sequencing. F461's inspected init path reaches a wrapper that waits for `/dev/ttyRPMSG30` before requesting bt_daemon, with separate normal/reduced stack declarations. Actual daemon working-mode consumers, provider binding, peripheral readiness and deployment are unproved. No SCS/IPC protocol or closed receiving/transport/authentication/session/framing body was analyzed.

The missing named F461 scheduler path/declaration does not prove absent scenario capability: alternative owners and third-party control remain questions. Likewise, F460 alarm_manager is a packaged name, not evidence of F454-style alarm wiring. Actual configured extra-partition contents and scene assets remain outside these downloaded images.

## One shared catalogue is not an installed-capability oracle

Both normal embedded `home/bticino/matrix_mx/MHCatalogue.db` files have SHA256 `bd2ff4d326692c85bc4eb3f86504d615758da97dc832389fac523734574833e9`. Their equal bytes coexist with different executable inventories. Stored catalogue metadata cannot replace evidence of actual consumer selection, configured features or Physical Device support.

The75-total scope includes SQLite's internal sqlite_sequence table; F461's narrower schema output lists74 noninternal application tables. Parent verification explicitly covers both scopes. Hashes preserve types and duplicate multiplicity without exporting raw rows. These differences are table-content fingerprints, not counts of new functions or stable-ID correspondences. Owner-aware semantic comparison and actual reader/filter/fallback behavior remain open.

Per-product signature scans cover every extracted regular file, not only database extensions, and find one SQLite-header database per image. Unknown/encrypted/container formats and runtime-generated databases are not excluded. Host SQLite reads are immutable, query-only and trusted-schema-off; no firmware SQL process ran.
