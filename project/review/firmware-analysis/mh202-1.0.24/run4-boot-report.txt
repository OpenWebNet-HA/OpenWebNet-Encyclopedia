## Validator return contract and checksum

Original validator `0x13894` calls the header reader at `0x138cc`. Nonzero header-reader return yields validator0. Otherwise it passes the returned stream and declared length to checksum helper `0x1353c` at `0x13908`, then closes the stream. An exact `fclose` return−1 yields validator−1. On other close results it parses the stored decimal checksum, compares it with the computed result and returns0 for mismatch or the stored checksum value for equality (`0x13978..0x139b0`).

This is not a Boolean API: zero is both the mismatch/error sentinel and a possible equal stored checksum result. Negative return−1 is a close-error branch, yet startup's selected comparisons described below classify any nonzero return as usable. The checksum helper's own error0 can also overlap numeric data. No actual buffer/error/file fixture was supplied to original code, so these are explicit branch/namespace limits, not measured corruption or exploit claims.

The checksum helper uses a256-word table at `0x1a34c`. A second writer-side helper `0xae9c`, invoked at `0xb64c`, uses a byte-identical1024-byte table at `0x18b14`. Host verification reconstructed all256 entries from polynomial `0x04c11db7`. The selected normal helper starts at zero, folds bytes through the table with a left shift8 and top-byte XOR, folds the **observed processed-byte count** as successive low bytes, then complements the result. This is consistent with the POSIX `cksum` recurrence. Three private synthetic host-model values, including empty input and `123456789`, matched the independent host `cksum` utility; no firmware checksum helper ran.

The original read loop chooses chunks up to65536, adjusts the remaining request while the declared signed length exceeds its accumulated count, stops on nonpositive read and checks `ferror`. The saved pure model covers ordinary complete reads with small nonnegative lengths only. It does not model every signed-length boundary, early EOF, stream offset, actual short reads or error state. There is no separate final exact-observed-count-equals-declared-length comparison in the selected checksum return path: it folds the count it actually processed. This does not by itself establish any malformed input's full acceptance through the surrounding header/stream/archive operations.

## Writer order and exact checked failure guards

The selected writer function `0xb1f4` prepares its temporary payload earlier through delegated archive/locking operations, which this batch does not execute or fully validate. Its selected fresh static ordering is:

1. Obtain payload metadata and checksum through the separate helper call at `0xb64c`.
2. Request unlink of the primary, open it with raw flags66, format/write the header, seek to1024, and copy payload in1024-byte read chunks. Close primary after the loop.
3. Request unlink/open of the mirror, write the **same formatted header buffer**, seek to1024, and reread/copy the same temporary payload. Close mirror.
4. Request unlink of `/var/tmp/conf.zip`; the ordinary end stores result0 at `0xbccc`.

The two copies are sequential operations, not an atomic pair. No `fsync`/readback verification occurs inside these selected post-open writer spans; that scoped observation cannot settle filesystem/device durability or unexamined caller/delegate behavior. `open` failures are checked against exact−1 and yield result1. Both header writes and both payload writes test **exact−1**, not equality to requested byte count. Their selected error results are2 (header) and3 (payload). A zero/short-positive write therefore does not enter those particular−1 error branches; the report makes no claim that this occurred physically.

Payload loop continuation requires a positive `fread` result and zero `ferror` before attempting the corresponding write. A read error can exit the loop through the same ordinary continuation as EOF; close/lseek/unlink results in these selected spans are not compared to expected success before proceeding. This is a bounded static guard/order map, not an executed writer error campaign or an audit of every earlier open/lock/archive branch.
