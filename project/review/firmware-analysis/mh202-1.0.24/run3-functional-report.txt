## Actual OWRITE marker consumer

Original `libdomotica!OWRITE(char*)` begins at `0x8544`. Its PIC base computes to `0x12114`. The pool relations at `0x89dc/0x89e0/0x89e4` select:

```text
format: %s%s/DISABLED
prefix: /var/tmp/bticino/script/
name:   GOT-resolved Script global
```

The caller passes those values to sprintf at `0x85b0`, then the resulting pathname plus a local stat-output buffer to `0x9188` at `0x85cc`. That tiny original wrapper simply rearranges the arguments, sets version argument3 and tailcalls imported **`__xstat`** at `0x9194`. It is not a connection routine despite objdump's nearest exported-symbol label. See [owrite-marker-and-request.txt](owrite-marker-and-request.txt), [owrite-pools.txt](owrite-pools.txt), [stat-wrapper.txt](stat-wrapper.txt) and [safe-literal-evidence.json](safe-literal-evidence.json).

At `0x85d0..0x85e8`, **stat result0** takes the marker-found log branch, sets the function's return slot to1 at `0x8618..0x861c`, and branches to the return tail before any selected F formatting/write. A nonzero stat result takes `0x8624`, which formats `F %s\n` from the OWRITE argument and then calls write at `0x8688`. Return1 in the marker branch is an observed **source return value**, not proof that an action occurred successfully. This batch does not establish how each interpreter call site consumes or ignores it.

This is a concrete cross-area refinement: taskmanager's run1 disable function creates `/var/tmp/bticino/script/<record-name>/DISABLED`; enable unlinks that path. Run2 proved that selected event/start/always callbacks do not themselves test record+52. OWRITE now supplies a later consumer of a matching pathname. The join depends on **consistent configured names and runtime prefix**, correct global binding and accessible filesystem state. It is not observed gateway behavior.

## Scope of the marker finding and bounded R/P gap

OWRITE's marker guard is **action-specific evidence**. The selected OREAD prefix lacks such a guard before its first F write; this does not prove that all other code or actions ignore disabled state. TWRITE/TWRITEI, conditional transformations, sleeps and arbitrary configured actions were not audited as a disabled-policy matrix. The actual user-level meaning of disabling a scenario needs those separate consumers and actual configured scripts.

[bounded-write-sites.json](bounded-write-sites.json) records the direct ARM BL→write@PLT sites found in these **two files only**: one in bt_script and six in libdomotica. They include the S/F/E producers above and text-write routines. This batch did not identify a dedicated R/P producer corresponding to the reviewed receiver's state2/state3 first-byte branches. That is a **bounded unfinished join**, not proof that R/P is unreachable or unsupported: computed calls, other providers, generated values and configured text can remain relevant. No global archive/namespace sweep or connection/authentication investigation was used to turn that gap into an absence claim.
