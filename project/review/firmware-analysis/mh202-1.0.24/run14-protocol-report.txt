## Borrowed arguments and synchronous lifetime boundary

Composer entry `0x16dcc` pushes36 bytes and reserves212 bytes, so its fifth incoming vector argument is loaded from current SP+248 at `0x16de8`. It creates a new pointer table of `vector.size()*4` bytes (`0x16dfc..0x16e04`). For each element, `vector::operator[]` returns the string reference, `0x16e20` reads the first word of that binary's string representation, and `0x16e24` stores that character-data pointer in the table. These instructions borrow the string storage; they do not deep-copy payload characters into the pointer table.

At the actual builder call `0x16f14`, the original argument layout is:

| C-interface argument | Original source |
| --- | --- |
| r0 output object | same `D`, via composer fp |
| r1 WHO char pointer | holder at SP+204, loaded to r7 at `0x16eac` |
| r2 WHERE char pointer | holder at SP+200, loaded to r8 at `0x16eb0` |
| r3 DIM char pointer | temporary string at SP+188, loaded at `0x16ef4` |
| `[SP]` values char-pointer array | allocated table r6, stored at `0x16f10` |
| `[SP+4]` count | vector size, stored at `0x16f00` |

The original normal cleanup ordering is builder return, DIM string destructor `0x16f24`, pointer-table `delete[] 0x16f34` if nonnull, WHERE destructor `0x16f3c`, WHO destructor `0x16f6c`, composer return, caller by-value vector destructor `0x18e7c`, then original vector destructor `0x18e84`. Thus the selected synchronous builder call precedes release of these inputs on the normal source path. This is a source lifetime relation under ordinary same-build C++ string/container/allocation behavior, not executed allocation, successful runtime initialization, unwind analysis or a general memory-safety finding.

The libopen builder's retained entry/tail at `0xb680..0xb800` and immutable native run10 establish the endpoint contract that consumes these C strings. No C++ primitive is replaced/executed in this batch.
