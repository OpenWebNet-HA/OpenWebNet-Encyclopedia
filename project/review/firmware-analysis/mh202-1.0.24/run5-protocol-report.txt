## 1. Original object and second text: exact pointer relation

The concrete handler begins at`0x1523c` with a prologue establishing fp. At`0x1524c`, r3 becomes FP−28672. `0x15258` stores incoming r0 at `[r3−2232]`. The **original parsed-object slot** is therefore FP−30904.

Later, straight-line entry dataflow `0x15338..0x15354`:

| Original VA | Relevant operation |
| --- | --- |
| `0x1533c` | Reload original object pointer from FP−28672−2232 |
| `0x15340` | Add`0x5e00` |
| `0x15344` | Add`0x3c` |
| `0x1534c` | Store resulting pointer at FP−28672−2228 |

The **second-text slot**, FP−30900, thus holds `original_object+0x5e3c`. The saved `candidate-parser-raw-buffer-copy.txt` independently shows candidate libopen `CreateMsgOpen` forming that same object offset and calling strcpy into it at`0xb384..0xb390`. This is a provider-specific raw-buffer relation, not a libcommon/F454 object assumption.

The later loads at`0x1e908/0x1e924` use the second-text slot for strlen and `CreateMsgOpen` input respectively; the latter call is`0x1e928`. The input to this second parse is consequently an alias into the original object's raw buffer under the unchanged pointer/object premise. It is not a copied independent string in that slot.

This establishes pointer provenance, **not arbitrary object consistency**. An existing parsed WHO field and embedded text can only be treated as coherent under additional upstream construction/normalization/no-mutation assumptions. Full earlier parser eligibility and bytes at this address were not executed or proven for a supplied raw fixture.
