## 2. `call_nowait`: parent gets the fork result before exec confirmation

The complete176-byte original function is in `call-nowait-full.txt`.

It preserves its incoming argv pointer and calls imported `fork` at `0x22c4`. Comparison with zero at `0x22c8` immediately returns for **any nonzero** result at `0x22cc`. Under the ordinary fork contract, that covers parent PID and fork-error−1. No exec-success exchange is performed before the parent return.

Only the zero-result child branch requests closing descriptors3 through19, with no selected return checks, then loads argv[0] and calls imported `execvp(argv[0],argv)` at `0x2360`. If exec returns, it requests `exit(-1)` at `0x2368`. This is a child exit request, not a normal helper return−1 to the waiting parent. No actual descriptor, command lookup, executable, child or exit was produced.

The daemon's launcher calls this import at `0x14efc` and stores the returned value in child record+12 (`0x14f08`; `service-launch-return-storage.txt`). That stored number is not by itself exec confirmation or application readiness. Other launcher logic and service matrices are prior findings, not repeated here.

## 3. `call`: unsigned wait-status byte with unchecked delegate returns

The entire original helper is only48bytes (`call-full.txt`). Its exact dataflow is:

1. `0x2374` makes r5 zero. `0x2378..0x237c` computes a local pointer to SP+4 and stores that zero word there.
2. `0x2380` calls `call_nowait` with the original argument vector.
3. Without checking that result, `0x2384/0x2388` supplies the local word pointer and zero options to `waitpid` at `0x238c`; r0 still contains `call_nowait`'s returned number.
4. Without checking `waitpid`'s returned number or testing normal-exit/signal bits, `0x2390` executes **`ldrb r0,[sp,#5]`** and returns.

The original ELF is little-endian ARM. The returned byte is therefore byte1 of the local32-bit storage: `(stored_word >> 8) & 255`. This is a zero-extended byte, so a normal return through this instruction is in0..255. It is neither the raw wait-status word nor signed−1. The zero-initialized word is a positive source fact; a specific failed wait's actual writes or nonwrites remain a delegate/runtime question.

The helper also does not explicitly preserve fork-error semantics: a−1 from `call_nowait` is passed onward to `waitpid`, rather than immediately returned to its caller. There is no wait-error retry or independent error branch in this complete helper. This report does not claim which child a real kernel would report, actual scheduling, signal handling or a particular runtime error.

`host-process-return-model.json` demonstrates the byte arithmetic with six private illustrative status/return fixtures. Storage words `0x00000100` and `0x0000ff00` yield1 and255; a word with only low signal-number bits set yields0. Fixtures with delegate error and the initialized word unchanged yield0 **by that stated fixture premise**; this is not a claim that every real error leaves the word unchanged. These are pure host calculations, not injected original syscall results or firmware execution.

## 5. `call_daemon` has a different contract

The complete92-byte function is in `call-daemon-full.txt`. It calls fork, returns−1 on the explicit fork-error branch, and preserves the original positive PID in r4 on the parent route. That parent requests `waitpid(pid,NULL,0)`, ignores the returned number, then returns the preserved PID at `0x23f0`.

The zero-result child branch requests imported `daemon` with the then-zero arguments. A negative daemon result can return directly from this helper in that child (`0x23cc`); it is not the parent's child-status return. Otherwise it attempts execvp using the saved argv and requests exit(-1) if exec returns. No daemonization, process hierarchy or later execution was observed.

Thus `call_daemon`'s parent result and `call_nowait`'s parent result are PID/error-oriented source contracts, while `call` returns a status-storage byte. None of these parent numbers proves the eventual application is functioning. The full libc implementations, actual kernel/process/descriptor behavior and any overridden providers remain delegated.
