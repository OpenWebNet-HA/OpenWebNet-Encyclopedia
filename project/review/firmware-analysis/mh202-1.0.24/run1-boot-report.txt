These are location aids scanned in load segments; their surrounding code must be reviewed before inferring callers or behavior. Eight bounded actual neighborhoods are saved. **The container/header/checksum, fallback selection, write atomicity and FlagXML policy have not yet been reconstructed for MH202.** Paths alone do not transfer F454 persistence semantics.

New original `hal_board!0x9308` caches a classification derived by reading `/proc/cpuinfo`, finding its Hardware line and matching case-insensitive board strings. The saved original code/literal relation includes LAGO→6, BAIA→5, BASI→0 and additional board labels. The packaged uImage name and package architecture labels point to a lago build; they are not an observed physical board classification.

`check_extra!0x5f14` calls this board classifier. A board bitmask (`0x78e`) selects an immediate0 return for one group. Boards0/5/6 instead reach `Device::get_device`, then the recorded argument vector `e2fsck`, `-p`, Device-result field+50, through imported `call` at0x5f90. Other board values take an error return. This is a static filesystem-check delegate boundary: no check was run, and the imported `call` return convention is not assumed to equal raw `system` wait status.

## Package actions and distinct normal/recovery installation helpers

`package-actions.json` records the original `fwz.xml`: productMH202, firmware1.0.24, object model5.0.5, provider`btesuv3`. Under status value4 the listed action order is recovery firmware(action2), normal firmware(action1), extra4(action3), extra2(action4). Both firmware actions reference the supplied common `uImage`; their distinct `.ext3.gz` filenames are explicit. This is manifest intent, not a verified runtime transactional/rollback order.

The new `liblghal` exports separate `update_fs_recovery(char*)!0x7c34` and `update_fs(char*)!0x7dd0`. Their board dispatch has three classes:

| Board code | Selected low-level path |
|---|---|
|1,2,3,7,8,9,10|UBI command-vector path|
|0,5,6|Device-result/shell-template path|
|4 or unsupported/outside table|returns−1|

In the UBI branch, recorded original pointers build `ubiattach /dev/ubi_ctrl -m 3 -d 2 -O 2048` for recovery and `-m 5` for normal. Each then calls `ubiupdatevol /dev/ubi2_0 <incoming path>`, followed by `ubidetach /dev/ubi_ctrl -m 3` or `-m 5`. Calls are at0x7d00/0x7d30/0x7d5c (recovery) and0x7e9c/0x7ecc/0x7ef8 (normal). The first two calls check **exactly−1** and return early on that value. No argv command, shell or filesystem operation executed.

The other branch calls `Device::get_device`, formats a shell template with incoming path plus Device-result field+140 (recovery) or+170 (normal), and calls imported `system` at0x7d90/0x7f2c. The **entire two template literals are withheld**, with pointer location and SHA256 only in `hal-withheld-update-templates.json`, because packaged credential-bearing parameters must not appear in artifacts. No password, command template or full argv is retained. These branches return the delegate result; their callers and interpretation of success/status are not traced here. The report does not assign a wait-status bug or assume the `call` API has `system` semantics.

Low-level helpers are not the complete archive-ingestion/integrity mechanism. Caller authentication, package validation, CRC/hash/signature interpretation, selected board Device fields, recovery-kernel installation, update failure status and rollback policy remain open. In particular ZIP/header/payload checks inherited from provenance establish archive integrity checks, **not cryptographic authorization of the firmware**; no signature-absence conclusion is made from strings or from these selected install helpers.
