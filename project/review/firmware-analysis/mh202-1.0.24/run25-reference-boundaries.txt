# WHO25 reference boundaries for the MH202 continuation

This is a reading of four existing curated encyclopedia pages, preserved before integration. It adds no original firmware execution, specification-source review, oracle replay or physical observation. Exact pre-edit page hashes, snapshot paths and fourteen line/excerpt locators are recorded in reference-locators.json and the repository's reviewed/run24/WHO25_REFERENCE_PIN_SUPPLEMENT.json. The previous thirteen-document snapshot index is unchanged.

The existing WHO25 root reference explicitly separates multiple families: historical ScenarioPlus WHAT11..15, CEN+21..28, contact/IR31..32 and a ZigBee-specific33..37 family. These already published distinctions must not be collapsed into one parameter/address model. The CEN+ page's pushbutton/Object model, contact/IR address forms and ZigBee product-and-Unit grammar retain their own applicability. A new firmware-local prefix test or numeric mask does not redefine those domains.

The source code names trasv_cmd and a routing declaration for WHO25 are insufficient to assign physical meanings to internal bytes. The pending MH202 reports must derive actual registration criteria, directions, guards and fields from the supplied firmware. Reverse criterion9 is not automatically WHO9. Parsed kind, envelope status/type/metadata, private state and numeric WHAT remain different namespaces.

Any translated body/candidate string or postparsed private-state ledger remains conditional source evidence. Exact forward/reverse text symmetry between separately supplied examples is not a causal exchange, original parser acceptance or a physical ON/OFF/event result. A local software ACK/NACK helper request is not evidence of bus delivery or a Device state. A bounded family guard cannot establish gateway-wide support or absence, including absence of a different ZigBee interface.

The current curated CEN+ page contains separate published compatibility, inspected oracle-v3, historical oracle-v1 and physical MH200-capture sections. The older MH202 oracle-v1 and later oracle-v3 reply/output combinations belong to different recorded harness conditions. This overnight source examination has not re-fetched, reproduced or independently audited those external results. Its zero target-process/OS/gateway/bus count must not be combined with their recorded execution as new evidence. The current references also keep literal physical probes scoped to their bytes/setup and avoid namespace-wide rejection rules.

The MH202 implementation note should therefore link the new build-specific reports while preserving the existing command labels, address grammars, historical results and physical limits. It may state which original software paths were identified and which fields were modeled. It must not replace a public support table, rehabilitate an old oracle claim or certify a complete accepted command/address domain. Independent review and the wider Device gates remain separate.
