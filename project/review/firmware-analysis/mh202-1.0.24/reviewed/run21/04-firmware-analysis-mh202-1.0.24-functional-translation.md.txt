MH2021.0.24 contains distinct sound and alarm translation plugins with their own internal routing criteria and message formats. The selected paths below are static implementation evidence for the exact [firmware profile](mh202-1.0.24.md). The [auxiliary record-copy test](mh202-1.0.24-record-and-script-lifecycle.md#auxiliary-field-records-use-a-command-directed-copy) separately executes original parser and helper code. Internal bodies, generated OPEN candidates and physical observations remain different evidence classes.

## Native parsing of the generated candidates

Two fresh isolated sessions execute the original same-build pointer parser on the exact generated strings, starting with null output slots and no supplied parsed fields. Both return `0` and construct parsed kind `1` objects under explicit ordinary string, allocation and list models.

| Supplied text | Native parsed representation |
| --- | --- |
|`*5*27*##`|WHO5, WHAT27 and a NULL WHERE pointer; no parameter lists|
|`*22*1#1#0*1#1##`|WHO22, base WHAT1 plus ordered parameters `1`, `0`; base WHERE1 plus selector20 `1`, selector24 NULL|

The alarm's literal empty field is not replaced with `0`, `1` or an allocated empty string. The sound fields are decomposed without discarding their parameters. Coincident object addresses across sessions refer to separate private mappings. Input strings remain unchanged.

This closes local parser construction for those two supplied candidates, while leaving plugin invocation, raw SCS admission and physical meaning separate. The new list-storage primitive follows statically audited original GLib data/next/prev stores; GLib code itself is not executed. The two entries contribute `652` original visits, `45` declared primitives, `2` redirects and `2` return boundaries (`701` hooks), with four table-data setup relocations counted separately. See the [generated-candidate parser report](../../project/review/firmware-analysis/mh202-1.0.24/run21-protocol-report.txt) and [independent isolation review](../../project/review/firmware-analysis/mh202-1.0.24/run21-protocol-review.txt).

## Sound query and reverse text

Actual multimedia translation registration has reverse criterion `8` and forward criterion `22`; its callback chooses the selected conversions through direction pairs. Internal criterion `8` is not `WHO 8`. On one coherent parsed `WHO 22`, kind `2`, simple `WHERE 1` case, the candidate address helper leaves both selectors null. The original query-format branch produces `95008F9F`, wrapped as type `3`, representation `1`, SCS routing `8`.

A separately supplied brief body `90008F00` follows the selected character/type mapping. It constructs the complete WHAT text `1#1#0` and WHERE text `1#1`, then passes `*22*1#1#0*1#1##` to the text/list helper with routing `22`. That helper does not run the OPEN parser. Do not flatten the parameterized fields to WHAT1/WHERE1 or use this candidate to replace the published tagged-address grammar.

The forward allocation/helper stores copy the source ID but do not initialize status offset `52` in the selected body. The reverse output copies status and ID from its own input. These are local field-copy facts, not complete initialization, correlation or memory-safety conclusions. No volume, sound-source or ON/OFF meaning is assigned from these synthetic character values. See the [sound translation report](../../project/review/firmware-analysis/mh202-1.0.24/run20-sound-report.txt), [independent source review](../../project/review/firmware-analysis/mh202-1.0.24/run20-sound-review.txt) and [WHO22 reference](../../functional/who-22-sound-diffusion/).

## Multimedia query state and separate receipts

The actual multimedia STM has a selected application path for a coherent parsed kind2/WHERE1 query. Under source-derived ordinary-enabled and source/utility-disabled flags, it writes envelope metadata4/8 to `1`, appends the same record, stores its ID at private offset `300` and computes a pending byte at private offset `296`. Those are members of a `320`-byte private context, distinct from envelope and parsed-object fields.

The finite case supplies all fifteen checked status bytes as `1` and deadline words as zero. That gives pending1 and a `manage_timeout` return before source creation. It does not establish that initialized runtime queries always have no timeout: any checked status byte `9`, other deadlines or later state can change the path.

A separately supplied receipt must match the saved ID and nonzero pending flag. Matching status1 clears pending without the selected NACK or timer-destruction calls. Matching status2 clears pending, requests a local NACK and conditionally destroys/unrefs the stored source. ID mismatch does not take those changes. These local receipts are not physical sound acknowledgements.

A distinct parsed-kind4/matching-DIM route may request a timer with literal `1300`; it is not the selected kind2 query path. Its callback chooses a local receipt from pending state and calls a stored callback pointer. Actual timer firing, complete pending/deadline producers, callback consumers and ownership remain open. See the [multimedia state report](../../project/review/firmware-analysis/mh202-1.0.24/run21-sound-report.txt) and [independent current-source review](../../project/review/firmware-analysis/mh202-1.0.24/run21-sound-review.txt).

## Alarm status and the published command vocabulary

The alarm translator registers reverse source criterion `4` and parsed-output criterion `5`. These routing axes do not identify `WHO 4` and `WHO 5` as one system. A selected type3/representation1 record is split into four two-character slices. The synthetic body `00004209` avoids the separate special-prefix branch; opcode text `42` and status text `09` select literal `27`. The fixed format constructs `*5*27*##` and passes it with the existing record to the core parser/conversion helper.

The [published WHO5 vocabulary](../../functional/who-5-alarm/what.md) already labels `WHAT 27` as Stop programming. Preserve that label. This incoming-status software selection alone does not prove that physical programming stopped or make status `09` a universal programming-event value.

The candidate has a literal empty WHERE field. It is not normalized to `0` or `1`, identified as a published central target, or conflated with distinct published and touchscreen query forms. The later isolated parser case above constructs an actual kind1 object with NULL WHERE; downstream serialization and consumer behavior for that object remain unexecuted. Under normal parser/provider/list completion, the existing-record core path would replace its body with a parsed object and preserve status/ID; a prior WHO2 helper test is not WHO5 execution evidence. See the [alarm status report](../../project/review/firmware-analysis/mh202-1.0.24/run20-alarm-report.txt), [independent source review](../../project/review/firmware-analysis/mh202-1.0.24/run20-alarm-review.txt) and [reference-boundary reconciliation](../../project/review/firmware-analysis/mh202-1.0.24/run20-reference-boundaries.txt).
