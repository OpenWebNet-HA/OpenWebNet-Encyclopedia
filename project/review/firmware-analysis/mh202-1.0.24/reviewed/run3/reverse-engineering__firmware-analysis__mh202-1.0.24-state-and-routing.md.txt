The demonstrated daemon selector reads `MYRECOVERY` from an export of the current process environment. It does not demonstrate a consumer of the packaged `sp/Recovery` marker or a bootloader-variable reader. Exact value `yes` requests running-copy flag `2`; other values request `1`. Writes, readback, environment-file handling and status helpers retain their delegate/failure boundaries.

A readback value `2` reaches a route that requests working status `2` and invokes the child launcher. The namespaces remain distinct: running-copy flag, current working status, per-child XML `working_mode`, packaged `normal_status`, and the recovery marker are separate quantities.

The runtime configuration pointer initially names image-root-relative `var/tmp/stack_open.xml`. The packaged volatile-file rules declare a startup symlink to `home/bticino/cfg/stack_open.xml`; the applying script has existing-path guards and asynchronous link requests. This establishes the initial source policy, not a completed runtime link or identical effective XML. Later replacement/rewrite producers remain open. The selected XML text callback stores each child's `working_mode` into record `+8`. The actual launcher skips that record only when its saved current status equals `2` and the child mode equals `0`. Other current statuses do not apply this exclusion in that helper. Therefore a packaged child mode `0` is not a universal disabled flag.

On the packaged nine-entry list, the conditional status-`2` model selects openserver, scsserver and bt_device; the other declared model cases include all nine. These are launch-call choices, not successful children or readiness observations. Argument-table validity, `call_nowait` semantics, stored results, actual XML contents and later supervision remain open.
