# Four installer systems.sqlite catalogues: full structure and selected product constraints

The four recovered databases share the same nine-table schema but contain different product catalogue data. The F454 variant has concrete camera, alarm-zone/scenario and advanced-control editor declarations. Their scope is **installer catalogue/UI metadata**, not installed objects, active hardware, firmware protocol acceptance or a complete implementation of a named validator. Every table and every row participates in the variant comparisons before these selected findings are interpreted.

The strongest new distinctions are the F454's retained templates beneath six missing parent references; separate catalogue limits for VCT children, cameras and alarm structures; and actual touchscreen2.1 coordinate constants and control-behavior differences. Surrogate property/complex-row IDs shift heavily between variants, so changed IDs are not treated as changed product behavior.

This is eight application tables plus SQLite's AUTOINCREMENT bookkeeping table, not nine product subsystems. `SCHEMA_AND_COUNTS.v1.json` contains every CREATE statement, column declared type/nullability/default/PK position, index and index-column metadata, FK target/action, row count, observed storage-type distribution and complete logical row-bag digest for every table in every variant. There are no views or triggers. INTEGER primary keys in the seven AUTOINCREMENT tables are row identities; Settings.Key is its text primary key. sqlite_sequence has no declared PK and is explicitly compared by its unique name entries here.

Five declared child FKs use ON DELETE CASCADE: properties→items, complex properties→properties, behaviors→properties, item validations→items, and property validations→properties. `ApplicationItems.ParentApplicationItemId` has **no declared FK**. Cid and Id are also not declared foreign keys and are not identified as WHO, electrical bus numbers, firmware object offsets or universal protocol identifiers. Names, Cid, Id, parent IDs, property IDs and behavior selectors retain separate namespaces. Currency numeric fields are stored catalogue fields, not measured consumption or an inferred unit conversion.

Settings MaxItems is the text600 and MaxExtraDirectorySize the text512 in all four payloads; no size unit or enforceable device memory limit is inferred without a consumer. DeviceFirmwareVersion is1 only for1768_1.0 and2 for the other three. The Version fields contain separate2016-02-16 timestamp strings; they are catalogue data, not current installed firmware readings. Other Settings values are inventoried by key/type/length and included in exact comparisons without exporting their contents.

## Full variant comparison before semantic selection

`ALL_TABLE_PAIR_DIFFERENCES.v1.json` compares **all six pairs and all nine complete tables**, with exact key-presence differences and changed-column names for every changed common key. The schemas are identical across all pairs. The fifteen currency rows are identical across all four variants. The whole-table logical digests cover complete rows, including columns not selected for narrative; no whole raw dump of credential-related values is needed.

For example, comparing F454 against either2.1 screen by surrogate PK alone gives1397 changed common ApplicationProperties records and2631 changed common ApplicationComplexProperties records. Those numbers are **not feature differences**: many ownership IDs and insert-order identities changed. `LINKED_ITEM_COMPARISONS.v1.json` therefore also compares complete relation-linked item bags. It removes only the included objects' own generated PKs and FKs to their included owner; it retains every remaining property/complex/behavior/validation field, duplicate multiplicity and literal parent reference. This is an explicitly bounded normalization, not a universal graph-isomorphism algorithm or proof that identically named IDs identify the same runtime object.

The two2.1 screen variants have identical full rows in **five** tables: ApplicationItems, ApplicationComplexProperties, ApplicationCurrencies, ItemValidations and PropertyValidations. They differ in ApplicationProperties, Behaviours, Settings and sqlite_sequence. Exactly four property rows differ:1495–1498, the coordinate-scale constants below. Behavior comparison without its own generated BehaviourId yields242 shared rows, one additional row in1768 and two in1898. Their owner property IDs happen to align in this pair; that coincidence is not transferred to other pairs. The extra/missing declarations all use `IsEnabled`, selector `IsMixedModeGroup`, target `mode`, target text `False`, attached to different source property IDs. No predicate implementation or actual enablement is executed.

## Advanced controls: behaviors are explicit data, not evaluated predicates

F454 item224 advancedOpenCloseCommand has item Cid3017/Id3012, a separate property `cid` with initial text3017, and address property1474 implemented as PluginBasedAtt. Its PluginParameter rows include isPointToPoint False, isMultiple False, isEvoluted True and addressType1. Its selected firstAvailableFor `[11-1015]` is plugin-input metadata, **not** an ordinary integer protocol address range inferred from its endpoints.

Behaviours195/196 attach to that address property: `SetValue` with selector strings IsAMBGENGR/IsNotAMBGENGR requests target `cid`3018/3017. Other attached rows request pul0, visibility/enabled changes and mode0; behavior205 on mode requests ChangeApplicationItem to advancedOpenCloseCommandSafe when stored selector1 matches. The group's own item222 declares maxNrItems50/maxNrItemsInGroup16. Exact rows, including the parallel up/down and safe variants, are retained; no named predicate, plugin, property setter or conversion rule is executed.

This source evidence separates an item's static Cid/Id, a mutable property named cid, a behavior's target name, and emitted firmware/protocol identifiers. Inferring a universal command or physical semantics directly from any one of these integers would erase those namespaces.

## Cross-device coordinate and behavior evidence

The two2.1 screen variants have explicit coordinate constants1495–1498. The1768 values are roomXFactor1, roomYFactor1, profileXFactor1, profileYFactor1, with descriptions naming the Resistive screen. The1898 values are1.25,1.33,1.27,1.34 respectively, with descriptions naming Capacitive. These are stored transformation factors for room/profile sections as described by their own rows, not measured panel geometry or executed coordinate conversion. Their actual reader, rounding, units and application timing remain unclosed.

This is a concrete reason to retain distinct1768/1898 variants even when many tables match. The limited2.1 behavior differences are likewise source declarations, not proof of a physical difference in actuator support. The1768_1.0→2.1 item/behavior/property additions are fully represented by the complete comparisons, but a complete release feature table or release-wide runtime contract is not derived from row count differences.

## Reproduction, confidence and remaining consumers

Run `python3 -B work/installer-database-analysis/2026-10-31/systems/collect_systems_v1.py --check`. This reconstructs schema, full comparisons, normalized relation-linked comparisons, selected data, expression/type inventories, exact SQL/safety and input identities. Successful checks are read-only; first generation refuses existing evidence and freezes report/collector/outputs immediately. Snapshot membership and hashes are calculated before opening the snapshot index, avoiding circular inclusion. Older inputs/dossiers and repository pages are unchanged.

High confidence: original payload identities/member attribution, full schemas/counts/relationships, all-pair equality/differences, actual selected metadata and bounded graph/range parsing. Conditional: device/package applicability, the meaning/action of named UI/plugin/validator consumers, serialization and installation. Unknown: evaluated expression behavior, active configured objects, actual generated files, dynamic camera/alarm state, hardware/electrical associations and universal protocol limits.

The next useful source work is the catalogue reader/serializer for OnAddNewItem, VideodoorAddressControl and behavior predicates; the exact handling of retained disconnected templates; and the coordinate-factor consumer. It should preserve the difference between a UI-template declaration, a validator name and the actual firmware/runtime path rather than treating the database as executable proof.
