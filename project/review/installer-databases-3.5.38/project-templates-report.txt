## Complete schema and declared local relationships

The collector inventories every table, column/type/nullability/default/PK position, index and declared FK; computes all-table logical-row hashes/counts; and checks quick_check and foreign_key_check on both exact files. It records142SQL/PRAGMA queries. Neither original application FK-enforcement settings nor actual insert/delete/assignment behavior is executed. Successful FK checks describe the shipped small/empty dataset, not a populated project or comprehensive application constraint audit.

MHPrj's positive declared graph includes:

| Child/table | Declared referenced structure | Source role/boundary |
| --- | --- | --- |

Both CONF tables have two-part primary keys combining a named configuration key with the owning runtime-row ID. The Object table separately stores id_rt_object, key_object and slot. The schema therefore positively distinguishes these storage concepts. Empty instance tables leave catalogue/protocol joins and actual persistence code unproved; matching column names or numeric values are not sufficient.

PTDB declares EN_AREA.area_type_id→EN_AREA_TYPE and area_type_category_id→EN_AREA_TYPE_CATEGORY. AS_AREA_HOST references both EN_AREA and EN_HOST and has a composite(area_id,host_id,progressive) key; the meaning/order policy of progressive is not executed. AS_AREA_RELATIONSHIP has separate parent/child FKs to EN_AREA. These are local declared relations, without proof of a complete tree-validation or multi-host application policy.

No cross-file FK or populated bridge connects PTDB to MHPrj or either to ScenarioSuite's79table schema. In particular, MHPrj RT_DEVICE.id_device is INT while PTDB EN_HOST.id_device is varchar(50); neither name proves they refer to the same identifier. MHPrj's local id_rt_area FK target is RT_AS_AREA_TYPE, so absence of a literal RT_AREA table is not a missing-target conclusion.
