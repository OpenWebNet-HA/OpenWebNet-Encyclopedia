# MH202 1.0.24 implementation

MH202 Firmware `1.0.24` implements scenario control through `bt_taskmanager`, executes script statements through `bt_script`, and uses separate COSO plugins for functional translation and request state. These components explain different parts of the [MH202 scenario programmer](../../devices/definitions/own-dev-0151-mh202-scenario-programmer.md); a shared WHO value or class name does not make them one engine.

The evidence is static implementation analysis supplemented by isolated execution of selected original helpers under explicit models. It establishes the behavior of identified local paths, with complete Firmware runtime, installed Configuration and physical behavior still unobserved.

## Scenario engine and WHO 17

The native post-parser dispatcher maps the four ordinary scenario commands to distinct helpers.

| `WHAT` | Selected operation | Applicability |
| ---: | --- | --- |
| `1` | Launch | Existing record, nonzero WHERE and state/global guards |
| `2` | Stop | Selected record or general-WHERE iteration; child/FIFO policy is separate |
| `3` | Enable | Changes the record's disabled marker |
| `4` | Disable | Changes the record's disabled marker |

Execution/control status `1/2` and availability status `3/4` come from separate fields. A nonzero control field can describe pending or stop-request state, so a formatted execution status does not establish that a child process is running. The [WHO 17 reference](../../functional/who-17-scenario-management/) remains the canonical public vocabulary.

The native loader searches numbered paths `extra/4/<number>.spt/<number>.spt` for numbers `1..300`, continuing across failed opens. It binds Start, Stop, Enable and Disable trigger declarations to their own callbacks and prepares interpreter/FIFO arguments. The PHP index instead scans `scenario_1..scenario_300` in `info.xml`, stops at the first empty name and sends each record's separate XML `id` as WHERE. Neither enumeration defines a universal `WHO 17` address validator. [Scenario control evidence](../../project/review/firmware-analysis/mh202-1.0.24/run1-functional-report.txt), [web consumer evidence](../../project/review/firmware-analysis/mh202-1.0.24/run1-web-report.txt).

Saved-active records are relaunched on the inspected startup pass only when `$RESTART=SI`; the separate always-start pass uses `SEMPRE`. Configured panic, disabled-marker checks, query readiness and saved-state restoration have distinct guards, described in [scenario state and routing](mh202-1.0.24-state-and-routing.md). These local policies do not establish complete OnlyIf, panic recovery or automatic rerun after every completion.

## Routing, parser layouts and diagnostics

MH202 includes several parser implementations with different layouts and kind values. A parsed object must be attributed to its actual process/provider before another helper's fields or predicates are applied.

| Parser family | Selected representation | Interpretation limit |
| --- | --- | --- |
| `libopen` | Fixed C++ fields with `90`-byte address slots | Layout differs from `libcommon` despite similar method names |
| `libcommon` | Fixed C++ fields with `130`-byte address slots | Its measure-kind value is not the COSO query kind |
| COSO `libopenmsg` | `48`-byte pointer/string object | Selected commands and DIM queries produce kinds `1` and `3` |

Static dependency/symbol analysis supports different candidate parsers in `bt_device` and `openserver`; effective loader binding remains conditional. The diagnostic-family mask includes WHO `1000`, while the generic WHO-to-SCS map has no such entry. A General-class branch supplies its own header, so generic-map absence cannot establish global rejection. Detailed [diagnostic routing](mh202-1.0.24-state-and-routing.md#diagnostic-translation-and-completion) keeps parsing, member selection, collection, local result codes and output delivery separate.

## Configuration and recovery

Runtime configuration selects child modes, web/SDK flags and default-file paths. Normal/recovery selection uses a process-environment value; it is not established as a consumer of the packaged recovery marker or a bootloader variable. Primary and mirror Configuration containers, checksum tests and fallback selection have concrete local request policies, with partial I/O, copy outcomes, durable recovery and full update policy unresolved. See [Configuration and service selection](mh202-1.0.24-state-and-routing.md#configuration-and-service-selection).
