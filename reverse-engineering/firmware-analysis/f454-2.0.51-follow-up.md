# F454 2.0.51 identity and client representations

The F454 implementation distinguishes declared gateway identity, temperature representation, energy-frame lifetime and video configuration. These findings apply to [Firmware `2.0.51`](f454-2.0.51.md), using source inspection and conditional host derivations. They do not establish installed values, live browser behavior or physical measurements.

## Reference

| Subject | Established relationship | Unresolved relationship |
| --- | --- | --- |
| Gateway `N_CONF` | Packaged `mynconfdiag=15` reaches conditional getter/setter paths | Meaning of `15` and actual persistent value |
| Temperature representation | Short unsigned codes are preserved as digits; selected client formatting interprets four-character strings numerically | Actual physical production and validity of exceptional codes |
| Direct DH candidate | The selected local candidate is not returned to its direct caller's output route | Other producers and physical DH support |
| VDE controls | Discovery and camera-status consumers have separate gates | A controlling consumer of factory `communication/vde_enabled` |

## Packaged identity declaration

The packaged `/art.xml` declares `mynconfdiag=15`. The HAL XML callback recognizes the `root/art1` context and retains the text in its parsed result. A selected `configure_device(bool)` path passes that value to `hal_set_nconfdiag`. A separate synchronization path can prefer a codename-specific file, compare its parsed value with the getter and request a setter on mismatch.

This explains a source of the cached/persistent gateway value. It does not establish actual parser execution, file selection, successful storage or a count of physical configurators. The value `15` is neither a proved sentinel nor a Module count. [Identity source evidence](../../project/review/firmware-analysis/f454-2.0.51/targeted-identity-report.txt) supports the build-specific relationship; [Device Identity](../../diagnostics/dim1-device-identity.md#address-context) gives the canonical address-context distinction.

## Temperature conversion and client representation

The selected short B5 decoder reconstructs an unsigned byte plus `256`: bytes `F5..FF` become `501..511`, formatted as `0501..0511`. That formatter does not clamp, sign-convert or substitute a special value. Whether a physical probe produces those codes is unresolved.

The packaged client converter drops the first character of a four-character string and treats the remaining three decimal digits as tenths. Equivalent logic is present in the frontend bundle selected by `index.html`. The following are **conditional host derivations**, not captured readings or executed browser results:

| Input string | Derived Celsius label | Significance |
| --- | --- | --- |
| `0501..0509` | `50.1..50.9°C` | No interval-specific sentinel mapping in this converter |
| `0510` | `51°C` | Ordinary formatting omits `.0` |
| `0511` | `51.1°C` | Numeric representation does not establish physical validity |
| `0000` | `-°C` | Numeric zero fails the renderer's truthiness test |
| `1010` | `1°C` | Leading character is discarded, unlike the historical signed converter |

The [backend-to-renderer path](f454-2.0.51-continuation.md#json-event-to-renderer) preserves the selected scalar strings. The representation difference therefore exists in the inspected software path, while a live negative-reading display defect remains unobserved. Short unsigned `DIMENSION 0` and signed extended `DIMENSION 15` are separate routes.

The setpoint control is independent: indices `1..71` use `0.5*i + 4.5`, giving `5..40°C` in `0.5°C` steps. Measured-value pass-through does not widen that domain. Missing translation resources do not supply a physical error meaning. See the [temperature evidence](../../project/review/firmware-analysis/f454-2.0.51/targeted-temperature-report.txt), [explicit host examples](../../project/review/firmware-analysis/f454-2.0.51/targeted-temperature-model.json) and [canonical temperature dimensions](../../functional/who-4-temperature-control/dimensions.md#f454-2051-implementation-boundary).

## Direct DH energy candidate lifetime

The selected direct-DH handler formats an OPEN-looking candidate in local stack storage and then returns `0`. Its direct caller tests that result and resumes receiving, bypassing correlation/output processing. The candidate is neither a returned string nor the caller's output Object; erased stack bytes are not required for this lifetime conclusion.

A distinct outgoing `4xx` query route formats an internal request, records request state and calls a send helper. Its request-state return does not prove delivery or a physical query/reply association. The selected incoming discriminator's internal category is separate from an OPEN frame kind or WHO.

The `401..428` formatter table is therefore insufficient to advertise emitted responses on the inspected direct route. This does not establish universal lack of DH support or the absence of another producer. The [energy source evidence](../../project/review/firmware-analysis/f454-2.0.51/targeted-energy-report.txt) and [canonical energy scope](../../functional/who-18-energy-management/dimensions.md#f454-2051-direct-dh-path) retain the exact branch conditions. The distinct old-format publication path is described in [energy dataflow](f454-2.0.51-continuation.md#old-format-energy-producer).

## VDE controls and unresolved enablement

Generic XML readers do not identify a consumer of every factory leaf. Concrete PI/WebSrv callers consume sibling `vdes/guardunits/item` and `vdes/alarmlogger/{enabled,address}` settings; they do not establish a consumer of `communication/vde_enabled`.

The camera frontend separately tests auto-switching and the `get_vde_iu_status` response. A string `0` at split index `4` permits its camera-switch request under the other guards. The initialized request is `*#8**35##`; [video-status ownership](f454-2.0.51-av-and-board.md#video-status-response-ownership) identifies its selected response-field source. A client condition does not establish active camera service or the meaning of every status word.

The inspected scopes do not identify a literal-key consumer of `vde_enabled`; constructed keys, optional assets and runtime replacements remain possible. Factory default, WHO 8 role, board profile, discovery, process eligibility and camera status must remain separate. See [media configuration evidence](../../project/review/firmware-analysis/f454-2.0.51/targeted-media-report.txt) and [WHO 8 camera availability](../../functional/who-8-video-door-entry-telephony/README.md#f454-2051-camera-availability-path).

## Evidence limits

Actual temperature production, complete DH transactions and a controlling factory-enable consumer remain unresolved. Missing persistent/optional assets, effective initialization and running browser/process behavior limit source-only conclusions. Exact source identities, locators and preserved interpretation history are in the [supporting evidence](../../project/review/firmware-analysis/f454-2.0.51/targeted-provenance.json).
