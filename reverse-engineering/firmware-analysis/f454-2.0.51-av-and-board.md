# F454 2.0.51 video status and alarm serial attribution

F454 Firmware `2.0.51` has a video-status producer separate from its AV mode word and a selected serial path associated with the alarm software profile. Source evidence connects these components without equating private state, Linux device names or documented electrical connectors. Product roles and physical arrangements remain in the [Device definition](../../devices/definitions/own-dev-0002-audio-video-web-server-gateway.md).

## Video-status response ownership

The selected DIM35 formatter belongs to `bt_answering_machine`, not the separately examined `bt_vct` mode word. Its input path requires a message discriminator, parsed object, nonzero private route gate, WHO 8 dispatch, absent WHAT, dimension 35, selected category/selector checks, parsed kind 3 and a client-registration return 0.

The response format is `*#8**%d*%d*%d*%d##`:

| Response component | Source |
| --- | --- |
| Dimension | Literal `35` |
| First value, split index `4` | Same private object's word `+0xac` |
| Second value | Private word `+0x238` |
| Third value | Private word `+0x244` |

The source requests command and monitor publication before releasing the formatted string. Publication and delivery are separate outcomes. The camera frontend requests `get_vde_iu_status`, reads split index 4, and under its auto-switch condition requests `switchOnCamera` when the string equals `0`. With delivery of that same response, this connects the frontend condition to the private word `+0xac`. It does not prove camera availability, activation or a physical interpretation of every value.

## Selected private-state producers

Zero-allocation initializes the selected object's route gate and three response words to zero, subject to ordinary allocation. Later source paths can change them:

| Path | Selected effect | Scope |
| --- | --- | --- |
| WHO 1013 caller to locally named `manage_who_thirteen` | Up to six supplied values enter private fields, then route gate becomes `1` | Literal caller WHO is `1013`; an empty value list can also reach the gate write |
| `end_floor` | Status word `+0xac=2` | Same object obtained through the supplied argument record |
| `late_stop` | Selected branch writes `+0xac=4`; another writes `0` and clears the other two response words | Its own private-state guards |

These are local state assignments, not a universal mode table. The route gate, status words, configured role, answering-machine permission, discovery and `bt_vct` mode remain separate. The [AV producer evidence](../../project/review/firmware-analysis/next-investigations-2026-10-31/f454-av-producers-report.txt) and [source review](../../project/review/firmware-analysis/next-investigations-2026-10-31/f454-av-producers-source-review.txt) identify exact components and guards.

## Alarm serial node and board records

The selected `scsai` software profile supplies `/dev/ttyS2`. In the original image that character node has major `4`, minor `66`; the packaged driver uses `ttyS`, major `4`, base minor `64`. This corroborates line index `2`, independently of runtime allocation and any SoC UART number.

The original kernel targets DM365/BASI and configures three 8250 ports:

| Platform record | Address word | Interrupt | Registration identity |
| --- | --- | ---: | --- |
| DM365 record 0 | `0x01c20000` | `40` | `serial8250`, platform ID `0` |
| DM365 record 1 | `0x01d06000` | `41` | Same two-record table |
| Separate BASI record | `0x04000000` | `65` | `serial8250`, platform ID `1`; clock `8000000` |

The BASI initializer requests DM365 registration before its separate record. Under successful probes, normal slots 0/1, no intervening match/override and available slot 2, that separate record can occupy line 2. Platform ID 1 does not itself select tty index 1 or2.

Pinmux labels `UART1_RXD_34` and `UART1_TXD_25` identify source mux records, not PCB/connector pins or the separate BASI wiring. `/dev/ttyS2` must not be restated as DM365 UART2. [Board/driver evidence](../../project/review/firmware-analysis/next-investigations-2026-10-31/f454-alarm-board-report.txt) and [source review](../../project/review/firmware-analysis/next-investigations-2026-10-31/f454-alarm-board-source-review.txt) retain exact record and allocation conditions.

## Evidence limits

Actual serial allocation and the electrical link to `SCS AI` remain unresolved. A board net map or independently justified resource description linking the separate address/interrupt to that interface would discriminate the attribution.

The video response owner is established within the inspected path; full private-state lifecycle, initial role 1 activation and documented camera/answering-machine conditions still need corroboration. A controlled status exchange would test those relationships. Separate [application database declarations](../../internals/device-application-databases.md) do not populate dynamic status words or identify terminal wiring.
