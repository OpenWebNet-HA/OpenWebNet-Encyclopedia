# F460 and F461 Firmware composition

F460 `2.0.12` and F461 `2.0.11` share a packaged platform and an identical embedded catalogue, but have different application inventories and selected binary implementations. Their main applications use AArch64. Firmware-specific object layouts and consumers therefore require their own evidence rather than [MyHOMEServer1 ARM32 layouts](myhomeserver1-3.87.13-research-synthesis.md).

## Different packaged applications on a related platform

| Packaged property | F460 | F461 |
| --- | --- | --- |
| Selected main program ABI | AArch64 ELF64 | AArch64 ELF64 |
| Named scheduler, alarm, energy, player and `bt_netatmo` executable paths in normal image | Present | Those five exact paths absent from the inspected normal regular-file inventory |
| Normal stack process declarations | `25` | `17` |
| Embedded catalogue | Same payload in both builds | Same payload in both builds |

Selected common binaries differ in complete bytes. That does not identify which functions differ; common names likewise do not establish identical behavior. Normal and recovery images have their own startup/data environments, and minority ELF architectures also occur in the packages.

Corresponding device-tree payloads match while kernels and auxiliary-core payloads differ. A tree's model/compatible strings are descriptions, not proof of the selected hardware or active tree. The selected F461 startup wrapper waits for `/dev/ttyRPMSG30` before requesting the daemon; this declaration does not establish peripheral readiness or successful startup. Exact platform/source details remain in the composition evidence.

The inventory difference does not establish absent F461 scenario capability, and a packaged F460 alarm-manager name does not establish F454-style wiring. Configured extra-partition contents and populated scenes are not supplied by these images.
