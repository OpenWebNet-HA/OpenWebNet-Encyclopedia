# MH202 scenario resources and panic Configuration

MH202 scenario Configuration distinguishes Start, OnlyIf, Stop, Action, restart and panic behavior. Recovered manufacturer resources identify the relevant ScenarioSuite profile and an enable-controlled panic conversion rule; Firmware `1.0.24` reads the same panic leaf and compares the resulting frame text.

These are declarative and implementation relationships. Alarm reactions in an MH202 scenario do not establish alarm arming/disarming or the F454's dedicated alarm-port role. The [MH202 Device definition](../../devices/definitions/own-dev-0151-mh202-scenario-programmer.md) remains the product reference.

## Manufacturer resources and applicability

The original MyHOME Suite `3.5.38` installer contains package `1902_1.0_LGG` and the following source families.

| Resource | Established role | Applicability limit |
| --- | --- | --- |
| `Scen_SuiteDB_ENG.db` | [Editor permissions, command rules and address profiles](../../scenario-engine/scenario-suite-database.md) | Shipped rules and empty working tables are not a configured project |
| Director, SDC and project-conversion XML | Declarative project/conversion structure | A declaration does not prove converter execution |
| Default/restoration `4.xtz` | Selected ZIP directories contain `4/extra.xml`, without `.spt` or `info.xml` entries | Not identified with the separately referenced Firmware-download payload |
| Restoration `2.xtz` | Metadata and language PHP members in the selected directory | Download-resource identity and installed contents remain unresolved |
| ScenarioSuite assemblies | [Database consumers and script writers](../../scenario-engine/scenario-suite-generator.md) | Static methods do not supply an executed export or accepted complete script |

Suite release, device package, catalogue default `1.0.0` and Firmware `1.0.24` are different version scopes. Matching BT/LG/LGG labels or archive basenames does not establish compatible content. No `.spt` or basename `info.xml` occurs in the selected installer-index/ZIP listings; opaque, encrypted, nested and dynamically generated resources remain outside that finite result.

## Panic declaration reaches the same Firmware leaf

| Configuration declaration | Value or operation |
| --- | --- |
| `P50`, `panicKey/enabling` | Default string `0` |
| `P51`, panic command | Default `*15*00*01##` |
| Hidden `P52`, target `panic` | Empty default target |
| Project-to-Configuration rule | When enabling equals string `1`, copy `panicKey/command/action/open` to `configuratore/setup/sicurezza/panic` |

The native taskmanager reads that same target leaf. Full-frame string equality sets its command gate and requests stop for records with nonzero control state. Skipping this one conversion rule does not establish that the whole converter clears an existing panic value. Different leading-zero spellings remain different byte strings; neither the default frame nor a textual difference is an observed physical button event.

Configured panic, ordinary Stop, query readiness and saved-state `$RESTART` restoration are separate policies. Fresh-process zero initialization of the gate does not complete power-cycle recovery, because another working-mode path also sets it. The [state and routing reference](mh202-1.0.24-state-and-routing.md#event-matching-and-the-configured-panic-frame) describes those consumers and unresolved gate clearing.
