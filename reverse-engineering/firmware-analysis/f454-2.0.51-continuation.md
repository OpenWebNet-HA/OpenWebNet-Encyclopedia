# F454 2.0.51 protocol-to-client dataflow

F454 Firmware `2.0.51` has concrete links between received temperature representations, client event fields, old-format energy records and video discovery/status selection. Source inspection and explicit host examples establish the relationships below. Runtime callbacks, traffic and Physical Device behavior require separate evidence.

## Reference

| Area | Source relationship | Limit |
| --- | --- | --- |
| Temperature | Selected WHO 4 mappers preserve scalar strings through the event/cache/view path | No live reading or browser display observation |
| Old-format energy | Selected stream rows format records and reach parser/send requests | No established physical units, calendar or delivery |
| VDE discovery | A discovery-specific `vde` value selects seven target types | Not a factory media-enable or readiness flag |
| Camera-status request | The initialized builder produces `*#8**35##` | Response-field and role behavior have their own owners |

## Temperature frame to JSON

The selected `api-arm` WHO 4 paths create string-valued `who`, `where`, `eventName`, `eventType` and `actual_temperature` fields.

| Mapper | Extraction | Preserved representation |
| --- | --- | --- |
| DIM0 | Digits-only frame match followed by delimiter trimming | `0501` and `0511` retain their leading zero |
| DIM15 | General dimension parse, selector token `1`, then scalar copying | `1010` and `1501` retain their leading digit |

The DIM0 implementation uses a capture start pointer as a C-string suffix before trimming. Its comparison with `100` concerns a delimiter position, not a temperature threshold. Neither selected extraction-to-field path performs a sign operation or numeric conversion. [Backend source evidence](../../project/review/firmware-analysis/f454-2.0.51/continuation-temperature-report.txt) records the exact mappers and guards.

## JSON event to renderer

Both mappings use `cu_zone_set_actual_temperature`. On the selected frontend route, successful live-update data enters event processing; a burst passes the same event element to dispatch. Configured target lookup uses WHERE or the external-probe association, and the selected thermal models store the mapped field before controlled-zone/external-probe handlers supply it to the shared renderer. No compensating scalar sign conversion is present on this inspected handoff.

Matching object inventory, registered views and functioning callbacks/transport are prerequisites. General-WHERE and alternative model branches retain their own conditions. [Frontend evidence](../../project/review/firmware-analysis/f454-2.0.51/continuation-frontend-report.txt) pins the event and view paths.

Combining that preservation with the [client converter](f454-2.0.51-follow-up.md#temperature-conversion-and-client-representation) gives these **synthetic host derivations**:

| Source representation | Event scalar | Derived Celsius label |
| --- | --- | --- |
| DIM0 `0501` | String `0501` | `50.1°C` |
| DIM0 `0511` | String `0511` | `51.1°C` |
| DIM15 selector 1 `1010` | String `1010` | `1°C` |
| DIM15 selector 1 `1501` | String `1501` | `50.1°C` |

The backend preserves the leading digit that this renderer discards. Backend compensation is excluded for these selected strings; an observed negative-reading display defect is not established. Physical code meanings and valid setpoint domains remain separate. [Host examples](../../project/review/firmware-analysis/f454-2.0.51/continuation-temperature-model.json) retain selector rejection and ASCII/regex premises.

## Old-format energy producer

A `bt_supervisione` path accepts stream function `0x50`. Rows `0x10..0x14` map to dimensions `56`, `57`, `58`, `59`, `510`. The inspected ordinary cases are rows `0x10` and `0x14`, separate from newer DIM511..514 and the [direct-DH candidate](f454-2.0.51-follow-up.md#direct-dh-energy-candidate-lifetime).

Header/data classes carry a descending countdown and accepted-record counter. Their text area is reused as scratch storage:

| Stage | Selected row behavior |
| --- | --- |
| First accepted record | Replace text with two decimal byte values |
| Later ordinary record | Replace text with the current three decimal byte values |
| Terminal row `0x10` | Replace with the first two current bytes |
| Terminal row `0x14` | Replace with the first current byte |

These rows replace rather than cumulatively append; the append branch belongs to row `0x19`. For example, the corrected synthetic second record is `12*13*14`, not `10*11*12*13*14`. The [preserved correction](../../project/review/firmware-analysis/f454-2.0.51/continuation-energy-correction.txt) explains the superseded interpretation.

Intermediate and terminal branches reach parser/send requests when the selected descriptor is not `-1`. This establishes a publication route, not parser acceptance, delivered traffic or physical sample/calendar/tariff meanings. See [producer evidence](../../project/review/firmware-analysis/f454-2.0.51/continuation-energy-report.txt), [host sequences](../../project/review/firmware-analysis/f454-2.0.51/continuation-energy-model.json) and the [old-format consumer](f454-2.0.51-final-pass.md#old-energy-frame-to-consumer). A separate longer-DH publication path remains unresolved.

## VDE discovery consumer and initial status request

`bt_upnp` loads runtime stack Configuration and decimal-converts a selected discovery `vde` value. Its packaged declaration is `0`; the reader uses descendant-tag lookup rather than enforcing a strict XML path. Runtime values can differ.

When the resulting flag equals `1`, selected branches add seven device types to the search list: interface, switchboard, internal unit, alarm logger, server, external unit and generic VDE. Subject to initialization/registration, the control point requests searches for those targets. Other feature targets can remain active when this flag is not `1`. The same flag also gates selected detected-device handling through separate client-acquisition guards. These are discovery consumers, not media-process activation. [Discovery source evidence](../../project/review/firmware-analysis/f454-2.0.51/continuation-media-report.txt) identifies the exact settings and target strings.

The camera-status builder uses an initialized suffix `##`, giving `*#8**35##` after successful normal initialization and absent mutation. The selected `bt_vct` measure path reaches an acknowledgement tail rather than furnishing the missing status-field schema. That local result does not imply every Configuration receives only ACK. [Ordinary role routing](f454-2.0.51-final-pass.md#who-8-dim35-ordinary-role-route) and the separate [answering-machine response owner](f454-2.0.51-av-and-board.md#video-status-response-ownership) explain the distinction.

## Evidence limits

Factory `communication/vde_enabled`, WHO 8 role, board capability, discovery and service readiness remain separate. Actual old-history record counts, physical units, live signed temperature display and complete request/response routing require runtime or authoritative product evidence. The [source and review record](../../project/review/firmware-analysis/f454-2.0.51/continuation-provenance.json) retains reproducible locators and interpretation history.
