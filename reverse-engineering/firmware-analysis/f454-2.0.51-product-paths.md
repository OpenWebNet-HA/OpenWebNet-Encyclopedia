# F454 2.0.51 alarm and AV ownership

F454's separate alarm software lane and video mode state explain different parts of its OpenWebNet-facing behavior. The [Device definition](../../devices/definitions/own-dev-0002-audio-video-web-server-gateway.md) supplies documented `SCS AV`/`SCS AI` connector roles and conditional camera/answering-machine features. Firmware source identifies software owners; it does not establish electrical wiring or an active installation.

## Alarm software ownership

The packaged `scsai` alias resolves to `scsserver`. The executable derives its invocation basename and uses it as the XML application selector. A selected Configuration callback retains `serialchannel/device`, which becomes an `open` argument.

| Packaged profile | Serial pathname | Local server port | XML `bus_type` |
| --- | --- | ---: | ---: |
| `scsserver` | `/dev/ttyS1` | `20001` | `0` |
| `scsai` | `/dev/ttyS2` | `21001` | `1` |

These are source declarations and argument flow, conditional on active Configuration and ordinary provider behavior. They do not identify the electrical relationship between `SCS AI` and a numbered UART.

The separate `cosoai` wrapper requests `./bin/coso -c cfg/cosoai_cfg` in its intended working directory. Its packaged settings select `libcosoai`, `SCSEnable=0`, `SCSAIEnable=1`, port `21001` and client `46`. The AI plugin's enable-controlled path registers `scsai_field_bus` with criterion `34`; the core forwards the manager tuple into the initializer before a connection request. The alarm translator independently registers source criterion `4`, destination `5` and a callback; the alarm state plugin registers its WHO/system `5` callback.

This establishes positive local ownership and registration links. Natural serial-origin admission, active registry, effective binding and successful connection/session behavior remain unresolved. XML bus type, criterion `34`, source `4`, WHO `5`, client `46` and ports belong to separate namespaces.

An isolated original-helper result serialized a synthetic alarm object to `*5*17*#5##`; published WHO 5 vocabulary labels WHAT 17 Anti-panic alarm. It does not validate that synthetic WHERE as a configured sensor or establish physical alarm behavior. [Alarm source evidence](../../project/review/firmware-analysis/product-followup-2026-10-31/f454-alarm-report.txt) and [independent review](../../project/review/firmware-analysis/product-followup-2026-10-31/f454-alarm-source-review.txt) retain the implementation and fixture scopes.

## Concrete AV mode producers

The mutable `bt_vct` mode has separate constructor and command paths:

| Path | Selected assignment | Condition |
| --- | --- | --- |
| Role 1, base WHAT 37 | First WHAT parameter restricted to `1`, `2` or `3` | Parsed-object admission and destination-helper result other than `-1`; existing global mode must already equal `2` |
| Role 2, base WHAT 37 | Selected stores of `1`, `2` or `0` | Its own caller/admission/parameter policy |
| Role 1/2 startup | `-1` | Selected constructor path |
| Role 5 startup | Constructor `-1` overwritten with `1` | Both inspected `max_der` branches; that configured/default value is stored separately |

The role 1 command stores the first `#` parameter, not base WHAT `37`. Its existing-mode guard prevents this path from explaining an initial transition from `-1` to `2`. Role 2 and role 5 are separate routes; their code presence is not proof that a role 1 installation uses them. These assignments do not establish captured commands or physical mode meanings.

The frontend DIM35 field instead comes from a private `bt_answering_machine` word. Mode, role, factory enablement, discovery, answering-machine permission and camera availability must remain distinct. See [video-status ownership](f454-2.0.51-av-and-board.md#video-status-response-ownership) and [AV source evidence](../../project/review/firmware-analysis/product-followup-2026-10-31/f454-av-report.txt).
